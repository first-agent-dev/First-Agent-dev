# Памятка: как правильно готовить патчи для First-Agent
# (вынесено из граблей сессии 2026-08-08 — харденинг fa-update.sh + s13 conformance)
#
# Это НЕ абстрактные best practices — это конкретно те ошибки, которые я (агент)
# допустил в этой сессии, и правила, по которым больше нельзя поступать.

## 0. Контекст
Перед тем как писать код:
- Прочитать раздел про workflow в инструкциях пользователя: проблема → детальное изучение →
  конкретный план → patch → пользователь git apply/commit/push/fa update → live test.
- Изучать документацию в репо ПЕРВЫМ делом, прежде чем импровизировать.
- Помнить: пользователь работает через Remote-SSH, команды запускаются на fa@fa-HP в docker-
  контейнере через wrapper scripts/fa; обёртка не прокидывает произвольные env; на хосте sudo
  запрашивает пароль и НЕЛЬЗЯ ломать интерактивный tty.
- Два инструментальных чека ДО того как считать измерение валидным:
  * `uv run python -c "import fa; print(fa.__file__)"` → <repo>/src/fa/__init__.py
  * `uv run which pytest` → в .venv/

## 1. Сначала думай о РЕАЛЬНОМ сценарии исполнения, не только о «фича работает»
Патч v1 харденинга сломал sudo (и весь update) потому что я добавил `set -m` и `kill -KILL -- -$$`
и проверил только «флок не даёт второму инстансу зайти / cleanup шлёт сигналы» — но не проверил:
- что sudo меняет foreground process group и шлёт SIGTSTP самому себе, если запущен из другой pgroup;
- что `kill -- -$$` шлёт KILL всей группе, ВКЛЮЧАЯ родительский bash, если тот в ней же;
- что вообще существует интерактивный tty-сценарий (запрос пароля sudo), а не только pipeline/cron.

Правило: любая правка shell-скриптов, которые пользователь запускает интерактивно по SSH,
обязательно прогоняется mental-model через:
  (а) первоначальный запуск вручную в терминале с sudo;
  (б) повторный запуск, когда скрипт уже обновился (re-exec путь);
  (в) обрыв SSH посередине долгой команды;
  (г) параллельный запуск из двух tty (проверка лока);
  (д) cron/ansible/не-tty запуск (stdout не терминал, /dev/tty не существует).

## 2. Любая новая функция должна быть определена ДО первого вызова
Ошибка «_capture_tee_pid: команда не найдена» в v2 возникла потому что я вызывал функцию из
блока tee-редиректа на строке ~157, а определял её на строке ~220. Не прогнал даже базовый
`bash -n` c проверкой «все вызовы функций ссылаются на уже определённое имя».

Правило: после правки shell-скрипта обязательно:
  1. `bash -n FILE` — синтаксис;
  2. `grep -n '^foo()' FILE` и `grep -n 'foo ' FILE | head` — убедиться что definition line
     (где `^foo()`) идёт раньше любого вызова.
  3. Запустить сам скрипт с `--help` или в dry-run режиме в sandbox до того как слать патч.

## 3. Процесс-группы и сигналы в shell — это не место для творчества
- `set -m` включает job-control в неинтерактивном скрипте → оболочка создаёт новую pgroup;
  любая программа, которая меняет terminal foreground pgroup (sudo, ssh, readline), ломается
  (SIGTSTP, «Убито», повторные промпты пароля).
- `kill -- -$$` шлёт сигнал ВСЕЙ группе процессов с pgid == $$. Если сам скрипт в этой же
  группе (в т.ч. после `set -m`) — он убивает себя, а «отпускает» дочерних, которые на самом
  деле хотел прибрать.
- Детей, которых нужно прибрать на выходе, надо ТРЕКАТЬ ПО PID (через `cmd & PID=$!; wait $PID`),
  а не убивать всю группу скопом.
- `process substitution` (`>(...)`) в bash форкает subshell, где живёт tee/любая другая
  команда; PID такого subshell не ловится надёжно через `jobs -p` в неинтерактивных
  не-job-control сессиях. Не полагайся на это. tee сам завершается по EOF, когда родитель
  закрывает stdout — достаточно это проверить, а не пытаться убить его явно.

## 4. Локи и re-exec: не отпускай lock между «закрыть» и «переоткрыть»
Оригинальный баг:
  exec 9>&-             # отпустили flock
  exec bash script.sh   # ре-экзек
  # → в новом процессе делаем exec 9>lock; flock -w 600
В промежутке между `exec 9>&-` и `flock` в новом процессе другой экземпляр может забрать лок
(и забирает, если пользователь запустил второй fa update из соседнего окна или висит мертвец).
Решение — не закрывать fd 9, а передавать его число через переменную окружения и dup2-ить
в новом процессе (`export _FA_LOCK_FD=9; eval "exec 9>&${_FA_LOCK_FD}"`), тогда flock держится
непрерывно от первого взятия до завершения (включая re-exec).

Если нужен ре-экзек на новую версию самого себя — никогда не закрывай lock-фаилдескриптор
между старым и новым процессом.

## 5. Тестирование патча ПЕРЕД отправкой — не «синтаксис ок», а реальный прогон
До этого патча я:
  x не прогнал скрипт даже через `--help` с tee-редиректом и _capture_tee_pid;
  x не сымитировал блокировку (первый держит лок, второй получает не-блокирующий отказ);
  x не проверил, что sudo в tty-режиме не ломается.

Минимальный чек-лист для shell-патча до того как показать пользователю:
  [ ] `bash -n FILE` выходит с 0;
  [ ] для каждой новой функции — есть вызов ПОСЛЕ определения (ручной grep);
  [ ] файловые-дескрипторы и локи: сымитировать «держатель жив» и убедиться что новый
      инстанс сразу отказывает с внятной диагностикой;
  [ ] tee/buffering: вывести пару строк и убедиться что они появляются сразу (line-buffered
      через stdbuf -oL), а не только после завершения;
  [ ] tty/не-tty: если скрипт что-то пишет в /dev/tty — проверить оба сценария;
  [ ] re-exec путь: сымитировать «HEAD_CHANGED=1» и убедиться что ре-экзекнутый скрипт не
      встаёт на flock и не падает;
  [ ] сигналы: запустить короткий сценарий, послать SIGTERM, убедиться что дети прибираются,
      а скрипт не оставляет lock-файл занятым.

## 6. Инкрементальные патчи — знать на каком базисе построен дифф
Пользователь закоммитил мой v1-патч (с багом set-m) и запушил в origin/main, а я прислал
«полный» патч, построенный на pristine `103fb89`. Он не применился (контекстные строки не
совпали).

Правило:
- Если пользователь уже применил и закоммитил предыдущую версию, следующий патч должен быть
  либо (а) инкрементальным от того что сейчас у него в HEAD, либо (б) полный с обязательной
  инструкцией «сначала git checkout <КОНКРЕТНЫЙ_КОММИТ> -- <файл>» чтобы вернуть файл в базу,
  на которую дифф построен.
- Проверка: в sandbox `git clone → git checkout <TARGET_COMMIT> → git apply <patch>` выходит
  с 0. Если патч не применился на голый 103fb89 — переделать.
- Поле «index <hash>..<hash>» в заголовке git diff — это не декорация: это хеши blob,
  и по нему git проверяет базу. Если база в репо другая — патч не сядет даже при совпадающем
  окружающем тексте.

## 7. Не делать предположений о состоянии на хосте пользователя
Когда что-то не применилось / упало — спрашивать ВЫВОД конкретных команд, а не строить догадки.
В этой сессии дважды пригодилось:
  - у пользователя был закоммичен v1 патч (1dff6da), которого я не видел из sandbox;
  - `ps -ef | grep fa-update` показал реальных зомби после неудачных запусков.

Правило: прежде чем предлагать фикс — попросить (или выполнить через ssh) команды
диагностики: `git status`, `git log --oneline -5`, `ps -ef | grep ...`, `ls -la /tmp/...lock`,
`tail <лог>`.

## 8. Два патча подряд — сначала убедись что первый доехал и реально работает
Я сделал conformance-патч → начал делать fa-update hardening → наломал дров в харденинге →
пользователь не мог запустить fa update вообще, то есть не мог даже раскатить конформанс-
патч, ради которого всё и затевалось.

Правило: один атомарный патч — одна решаемая проблема. Не начинать следующий пока предыдущий
не доставлен на хост и не подтверждён живым `fa probe`/соответствующей проверкой.
Исключение — когда текущая проблема БЛОКИРУЕТ доставку (как сломанный fa update заблокировал
conformance patch); в этом случае фикс блокирующей проблемы делить на минимально возможные
итерации (сначала вернуть скрипту работоспособность, потом улучшать).

## 9. `noqa` — только с прямого разрешения пользователя.
В s13-патче один `# noqa: BLE001` на best-effort relocation debug-body файла — обоснован
(реально best-effort, нельзя ронять матрицу из-за ошибки переименования файла), и он был в
исходном коде в схожих местах; если бы добавлялся новый — спросить.

## 10. В конце работы — ВСЕГДА:
- [ ] Восстановить exec-биты: `git checkout -- scripts/` (или find ... -exec chmod +x), потому
      что sandbox сбрасывает биты;
- [ ] Полный `uv run pytest -q` на весь репозиторий (а не только на затронутые тесты);
- [ ] Проверить `git diff --name-only` — нет ли прилипших __pycache__, артефактов тестов;
- [ ] Проверить что patch действительно создаётся из текущего рабочего дерева и применяется
      на целевом HEAD (`103fb89` или на тот что у пользователя) в чистом checkout;
- [ ] Написать в чат ТОЧНУЮ последовательность команд с указанием ОЖИДАЕМОГО вывода после
      каждого шага, чтобы пользователь сразу видел если что-то пошло не так;
- [ ] Если это milestone — обновить HANDOFF.md.
