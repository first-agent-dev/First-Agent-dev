## 5. Findings — `just check` is RED

### F1 — `test_pyrefly_check_passes` fails; and the test is vacuous when pyrefly is absent · **HIGH**

```
pyrefly check found 4 errors:
  _PipedStdin.isatty / .close / .fileno  missing @override   tests/test_s10a_cli_coverage.py:1286,1289,1292
  `in` not supported between Literal['flow_state.json'] and int   tests/test_s8_workflow_controller.py:705
```

Attribution, measured per commit: `fc957f3` → 2 errors (**different** ones,
now fixed on main) · `0eb6129` → 1 error (the S8 one) · `origin/main` → **0** ·
`HEAD` → 4. So S10a's file adds **3** of the 4.

**Why nobody saw it:** the sandbox never had `pyrefly` installed — earlier
sessions used bare `pip`, not `uv sync --extra dev`. And the test's oracle is
`[l for l in result.stdout if l.startswith("ERROR")]` with the **return code
ignored**. I proved the failure mode directly: running a nonexistent module
gives `returncode=1, stdout=''` → **0 error lines → the assertion PASSES**.
A missing tool is scored as a clean bill of health. This is the same
"check that cannot fail" class this workstream has hit six times, and it is
*why* the 3 real errors went unnoticed.

Two separate fixes needed: (a) add `@override` to the three `_PipedStdin`
methods — S10a's own debt, trivial; (b) make the test assert `returncode == 0`
and that pyrefly actually ran. Note `just typecheck-advisory` prefixes pyrefly
with `-` (non-blocking) — but this **pytest** copy is inside `just test`, so it
*is* blocking. The two seats disagree about whether pyrefly is advisory: a
policy question, not an implementation detail.
