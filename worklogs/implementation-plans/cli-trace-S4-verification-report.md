## 3. Findings

### S4-F0 (reclassification) — V1 is reachable in production, not latent

**Severity: P0. Owner: S5. This supersedes the S3 disposition.**

S3 concluded V1 was latent: the per-instance lock holds, duplicates need a stale
long-lived handle, and `cli.py:1742` constructs its second handle *after* the
stage loop. That reasoning was correct for the workflow path but wrong as a
general claim.

Four shapes were tested during S4 analysis:

| Shape | Duplicates |
|---|---:|
| Sequential, second handle built after first finished (= S4.4) | **0** — structurally guaranteed |
| Two concurrent processes, natural start | **0** — startup jitter serialized them |
| Two concurrent processes released from a barrier | **7** |
| **Real production path** (`SessionManager → begin_run → EventLog`) | **6** |

The production-path repro:

```text
prod-a: ev-000016 .. ev-000022
prod-b: ev-000015 .. ev-000021      ← overlapping ranges
DUPLICATES: 6
```

Two guards were checked and neither prevents it:

- `reserve_run_binding` (`session_db.py:700-709`) is atomic but only guarantees
  unique **run-ids**; two *different* run-ids racing is exactly this case.
- There is **no lock, pidfile, or singleton** in `cli.py` or `manager.py`.
  Nothing prevents two `docker compose exec … fa run` from overlapping, and
  S4.4 proved multi-run-per-session is a supported workflow.

The barrier harness is the missing piece that makes S5's required
*"duplicate/concurrent event identity test is green"* non-vacuous: without a
synchronisation barrier, a concurrency test passes by accident.

### S4-F1 — `inner-loop-smoke` creates a second, session-less `session.db`

**Severity: P2. Owner: S6.**

`cli.py:874` calls `EventLog(log_path)` with **no `session_db`**. The constructor
(`state.py:154`) then creates `SessionDatabase(self.path.parent / "session.db")`
— a second authority at `<workspace>/.fa/session.db` with an empty `session_id`,
disconnected from the real `~/.fa/sessions/<sid>/session.db`. It is also the
**non-injected** `EventLog`, i.e. on the legacy mirror-fallback path — same class
as S3-F13.

Reproduced locally:

```text
created: session.db      injected session_db? False
session_id on the DB: ''    session_id column values: ['']
```

Not new breakage (pre-existing smoke-entrypoint design), but now **confirmed live
on the deployed container**, which S3 could not claim. Related: the parent plan's
S5 §Do-not already says *"do not introduce a second session DB under
`workspace/.fa/blackboard`"* — same concern, adjacent path.

### S4-F2 — `.gitignore` negation bug makes every `.fa/` artifact untracked

**Severity: P2. Owner: pre-S5 hygiene commit.**

```gitignore
 9  .fa/
10  !.fa/                       ← cancels line 9 entirely
11  !.fa/dependency_contract.toml
```

Line 10 un-ignores what line 9 excluded. Git cannot re-include a path inside an
excluded **directory**, so the intended allowlist never worked and all runtime
artifacts surface as untracked on every run. Reproduced in a scratch repo.

This is the real cause of the "changes from somewhere before" the operator saw
after each `fa-update` / `clean-rebuild` — not stale files. Deleting them does
not help; each session clone regenerates `.fa/` at runtime.

Verified fix (`.fa/*` instead of `.fa/`):

```text
session.db, smoke-events.jsonl, entrypoint-status.txt,
inner-loop-smoke.txt, telemetry/…, blackboard/…      IGNORED
dependency_contract.toml, host-bootstrap.json        VISIBLE
```

Line 11 also omits `host-bootstrap.json`, which **is** tracked — the allowlist
was incomplete as well as inoperative.

### S4-F3 — `fa-update.sh` chmod drift dirties 12 tracked files permanently

**Severity: P2. Owner: pre-S5 hygiene commit. — CLOSED 2026-07-29 (S7 §2).**

> **Closure evidence.** Fixed by `57f574a` (S5), which is exactly the remedy
> this finding proposed: `git show --stat 57f574a -- scripts/` lists those
> **12 files, mode-only, 0 insertions**. Re-measured 2026-07-29 — index and
> worktree agree at `755` for all 12, and `git status` is clean, so
> `fa-update.sh:872`'s `chmod +x` is now the intended no-op.
>
> The analysis below (index at `100644`) is **stale**; it described the state
> before S5. Recurring dirt seen in later sessions was sandbox filesystem
> drift re-materialising modes on a fresh container — same symptom, different
> cause. Re-verified rather than trusted, per the "notes are inputs, not
> authority" rule; the original text is kept for the record.

```bash
# scripts/fa-update.sh:872
find "${REPO_DIR}/scripts" -maxdepth 2 -type f \( -name '*.sh' -o -name 'fa' \) -exec chmod +x {} +
```

That pattern matches exactly **12 files**, identical to the 12 the operator saw
modified. Git's index records them as `100644`, so every `fa-update` run produces
a permanent mode diff that reappears after each update.

The container is **not** responsible: `/repo` is `read_only: true`.

Same **class** as S3-F8/V12 (tests chmod'ing tracked sources), now confirmed in
deploy tooling. Note the index is arguably the wrong side of the discrepancy:
`scripts/fa-entrypoint.sh` and `scripts/fa` must be executable to function, yet
are committed non-executable, and `Dockerfile.fa:102` papers over it with
`COPY --chmod=755`. Likely fix: `git update-index --chmod=+x` on all 12 and
commit, making the script's chmod a no-op.

`?? .fa/runs/` also appeared host-side but not in the container workspace —
a separate host-side artifact, covered by the S4-F2 fix.

## 5. Q12 evidence

S4.7 provides the operator-facing data Q12 asked for.

On the **happy path** the deterministic root is not silent: `_cmd_inner_loop_smoke`
prints three `OK:` lines directly. But those are `print()` calls in the CLI
command, not EventBus events — `run_session` itself emitted nothing, confirming
S3-F9 on the live path.

The asymmetry Q12 targets therefore appears only on a **stop** path: a hook
denial inside `run_session` writes a durable `run_stopped` row and produces
neither a `print()` nor a console event. The operator sees a session stop with
no explanation.

This supports **option (b)+(c)** from the Q12 analysis: record the exemption now
(the mirror contract should not claim a guarantee `loop.py` does not provide),
and let S6 decide whether the caller-side emit in `drive_session` is worth the
~10 lines. It does **not** support option (a) — wiring an `EventBus` into the
deterministic root would add a dependency to the one currently-pure path, and
S4.7 shows the happy path is already adequately narrated.
