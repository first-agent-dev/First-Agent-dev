# Тяжёлые ходы и tool batching: OpenCode v2 и First-Agent

Дата: 2026-11-01. Концептуальный разбор, не контракт, не разрешение на реализацию,
не закрытие Q107. Исходники OpenCode: релиз `v2.2.5`, commit
`9bbb8ce18c80f099e0e448775f59d965ead40a21`; наш репозиторий до этой заметки —
`6e953b6`. Просмотрены пути кода, отдельно выполнен локальный fault-injection probe;
измерений настоящего latency/throughput, теста OpenCode или managed host нет.

## Сначала различить уровни

1. **Несколько tool calls в одном ответе модели:** модель заранее указывает набор
   независимых действий. Между ними не требуется новый LLM call. Исполнение при
   этом может быть последовательным — число сетевых запросов к LLM уже уменьшено.
2. **Параллельное выполнение:** независимые операции реально перекрываются во
   времени. Это уменьшает latency, но требует отдельно доказать общие ресурсы,
   состояние и безопасности. Одновременное чтение mutable view не равно snapshot.
3. **Композиция зависимых вызовов без нового LLM call:** например, найти файлы,
   затем обработать именно найденные результаты, выбрать часть и вызвать следующий
   tool. Простой список готовых вызовов без переменных/условий этого не умеет.
   Порядок `write(fixed_path)`, `read(fixed_path)` может быть задан статически;
   выбор аргумента по результату первого вызова — нет.
4. **Результат/контекст:** единый внешний ход может породить много физических
   результатов. Лимит на каждый не является лимитом на всю сумму; агрегирование
   не должно стирать IDs, отказ/неопределённость, исходные данные или аудиторскую
   трассу. Больше инструментов на ход не означает обязательно больше текста в LLM.

## Что проверено в OpenCode v2.2.5

- Для обычных model-facing tool calls runner публикует вызовы, запускает каждый
  в своей fiber и затем ожидает результат всех: см.
  [step.ts:86–151](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/session/runner/step.ts#L86-L151).
  Системный prompt рекомендует распараллеливать независимые calls. Не доказано,
  что все доступные плагины безопасны при любых конкурентных эффектах.
- В этом теге найден отдельный **`execute` / Code Mode**, а не объявление
  отдельного встроенного инструмента `batch` в просмотренном core. Настройка
  старого `batch_tool` попала в unsupported experimental options
  ([normalize.ts](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/config/normalize.ts#L45-L52)).
  Исторический [batch v1.1.26](https://github.com/anomalyco/opencode/releases/tag/v1.1.26)
  не надо выдавать за доказательство идентичного механизма в v2.2.5. Возможно,
  пользователь имеет в виду другую сборку/плагин; вывод ограничен данным тегом.
- [`execute`](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/codemode/tool.ts#L74-L96)
  запускает ограниченный JS-подобный интерпретатор: `await` для зависимостей,
  `Promise.allSettled` для независимых действий, выражения/ветвления и составной
  результат. Каждая доступная внутренняя операция проходит dispatch/хуки; список
  вызовов и статусы сохраняются в результате/метаданных. Программа должна await
  нужное; начатое и оставшееся после окончания прерывается. Прерывание само по себе
  не доказывает откат или непроизошедший внешний эффект.
- Существенный нюанс: в этом теге встроенные [`read`](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/tool/plugin/read.ts#L38-L44),
  [`grep`](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/tool/plugin/grep.ts#L73-L79)
  и [`shell`](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/tool/plugin/shell.ts#L185-L190)
  помечены `codemode: false`: это **direct tools**, а не автоматически вызываемые
  из Code Mode. Список определяется snapshot/permissions
  ([tool.ts:265–314](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/tool.ts#L265-L314)).
  Нельзя обещать скрипт `execute { tools.read; tools.shell }` для этой версии.
- Ядро интерпретатора само не даёт прямой доступ к FS/процессам; host может добавлять
  capabilities/extensions, и конкретный OpenCode `execute` добавляет `fetch`.
  API поддерживает лимиты времени/числа вызовов/вывода, но их наличие в библиотеке
  не доказывает одинаковых default bounds на каждом пути. Их конкретная политика и
  потребление ресурсов не были проверены целиком. См. [README](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/codemode/README.md#L1-L20),
  [создание runtime](https://github.com/anomalyco/opencode/blob/9bbb8ce18c80f099e0e448775f59d965ead40a21/packages/core/src/codemode/tool.ts#L263-L277).

## Наш существующий фундамент

- `src/fa/inner_loop/coder_loop.py:1863–1874,1946–1954,2099–2122` уже принимает
  список tool calls из одного ответа LLM, передаёт их в один `run_session` и
  возвращает результаты по call IDs перед продолжением диалога. Код проверяет
  парность истории и при превышении ограничения формирует synthetic results.
  Следовательно, «несколько tool calls на LLM ход» уже предусмотрено; не нужно
  сначала проектировать отдельный batch tool.
- `src/fa/inner_loop/loop.py:32–71,127–165,188–249,315–405` группирует read-only
  операции, максимум пять потоков; записи, bash, invoke_workflow — отдельно и
  последовательно. Имеются индивидуальные BEFORE/AFTER hooks и упорядоченные
  результаты. В chat prompt есть соответствующее руководство
  (`src/fa/inner_loop/prompt.py:1083–1090`). Наличие этого кода не доказывает
  managed E2E, потокобезопасность всех backends и корректность под нагрузкой.
- `src/fa/inner_loop/runtime_limits.py:68–84`: role-less якорь — 6 вызовов на
  `run_session`, для активных ролей defaults 99 на время тестирования; это не
  оптимальный budget и не гарантия, что провайдер действительно выдаст 99 вызовов.
  `ToolSpec.max_context_bytes` — на результат, default 32768 bytes
  (`registry.py:340–365`). Пять больших результатов и 30 ходов создают суммарное
  давление на контекст и память; существующая projection/artifact — полезная основа,
  но сама не доказывает сквозную полноту, глобальный бюджет и изоляцию артефактов.
- `CellBackend` разделяет **cell/view episode**, а не обязательно создаёт новый
  workspace на каждую команду; у команд индивидуальные journal records
  (`src/fa/execution/backend.py:95–115,300–345`). Это выгодный фундамент для
  долгоживущей рабочей области. Однако `cell_worker.serve` допускает **один активный
  RUN**, а при занятости отвечает `None`, не очередит второй
  (`src/fa/execution/cell_worker.py:169–210`). Эти строки относятся к этому worker
  и не доказывают, что все независимые authority `READ_FILE` проходят через RUN.
- Путь managed search/reach ещё не интегрирован и Q97 не закрыт. Не надо обещать,
  что текущая верхняя параллельность прозрачно заработает поверх proposed EXEC
  helper: одновременные вызовы в один активный worker могут получить отказ/ошибку.
  На ближайшем шаге безопасная сериализация с честным поведением — допустимое
  ограничение, но не доказательство будущей масштабируемости. Нужны интеграционные
  испытания и явное решение на соответствующем стыке.

## Замеченные риски batching

1. **Retry после возможного выполнения.** `loop.py:395–403` при исключении общего
   parallel блока повторно dispatch-ит все допущенные calls последовательно. На
   локальном fake read tool через патч `wait` в момент после завершения двух
   handlers получено по **2 исполнения** каждого, а вызывающий получил два success.
   Это управляемая fault-injection проверка, не частотная оценка и не доказательство
   конкретного production-инцидента. Даже чтение может иметь telemetry/cache/I/O;
   при неидемпотентной операции такой fallback неприемлем без доказанной semantics.
2. **Таймаут не равен остановке.** Там же `Future.cancel()` не прерывает уже
   работающий Python thread, а выход из `ThreadPoolExecutor` context ожидает
   завершения. Название `exec_timeout` через 30 секунд не доказывает возврат к этому
   сроку и остановку эффекта. Это вывод из кода и семантики Python, отдельно не
   измерялось на managed host.
3. **`permission == read` не доказывает concurrency safety.** Fallback классификатора
   может допустить любой tool с этим permission; thread safety, ресурсные лимиты,
   побочные эффекты и политики нуждаются в отдельной проверке.
4. **Суммарные ресурсы и согласованность.** Пять одновременных memory-per-call search
   могут умножать пиковую память/CPU; не доказано, что все параллельные чтения
   видят один неизменный срез view при сторонних изменениях. Writes/PTY идут
   последовательно, но background descendants и внешние writers нельзя игнорировать.
5. **Тяжёлый ответ LLM — не транзакция.** Часть действий может завершиться до
   ошибки/отмены, последствия предыдущих не отменяются. Потребуются стабильные
   ID каждого эффекта, receipts и явное `unknown`; повторять всю группу нельзя.

## Экспертное мнение для Q107 и после I03

Сильная изоляция сама по себе не враждебна тяжёлым ходам. Враждебны ей дизайн,
при котором каждое действие теряет общий авторизованный view, состояние shell и
связь с историей, либо где параллельные операции безусловно сталкиваются в единой
очереди/ресурсах. Один workspace/cell может содержать сохранённый PTY-shell и
отдельные изолированные процессы/tools, каждый с собственной авторизацией и
результатом. PTY не нужно использовать как transport всего batch.

Для Q107 сохраняется предварительное предпочтение исследовать закрытый allowlisted
non-PTY helper в том же cell/view **при доказательстве инвариантов**, не перенося
его на host. Это не согласие пользователя на A, не разрешение на новую реализацию
и не гарантия одновременных helper calls: сначала должна быть продумана совместимость
с gate одного RUN, без тайных повторов и ложного полного результата. Доказанная
последовательная реализация может выполнять несколько подготовленных вызовов за
один LLM-ход, хотя она не даст ускорения от параллельности.

После завершения I03 отдельное проектирование: сначала использовать и измерить
существующий native multi-call, закрыть выявленные свойства его исполнения;
только при подтверждённой потребности рассматривать Code-Mode-подобную управляемую
композицию, с проверками каждого вложенного вызова через уже существующий
registry/authority, trace и ресурсные ограничения. Не добавлять заранее новый DSL,
планировщик DAG или общий доступ к host. Высокая стоимость ошибки, неполные
результаты и режим отмены при больших пачках должны быть оформлены до внедрения.

Гипотезу «30 продуманных вместо 100 атомарных» проверять не только числом LLM
запросов: качество/успех end-to-end, latency p50/p95, цена и входные токены,
cache, объём результатов, память/CPU, количество повторов, эффектов с неизвестным
исходом и цена восстановления. Большие батчи могут уменьшить сетевые round trips,
но увеличить переделку при неверном раннем предположении; число 30 не является
доказанным оптимумом.
