# W3 design draft: planner-owned acceptance custody and exact kill attribution

**Date:** 2026-11-10  
**Status:** DESIGN DIRECTION RATIFIED — operator selected artifact C and the Hollow-Facade, sealed-oracle, and honest pre-code-gate controls on 2026-11-10. Detailed implementation and production evidence remain open; this is not yet an ADR or implementation evidence.

## 1. Ratified scope

The operator selected the following behavior for the new W3 hard blocker:

- W3 cannot run candidate `fa update` until planner-authored acceptance-test custody and exact kill attribution are implemented and locally verified.
- The current v1 plan is an archival context artifact after I03; it is not migrated and no future compatibility path for that plan is required. Future plans use the new schema.
- W3 implements visibility mode A: the coder may inspect sealed tests, read-only. If no mode is configured, resolve and record A. Mode B (the verifier can execute tests whose implementation is hidden from the coder) is designed as a future configurable mode, not implemented in W3; selecting it before implementation must fail closed as unsupported, never fall back to A.
- For `TEST-DEFECT`, coder reports the potential defect against the pinned invariant and exact test. Planner either issues a new test revision plus a short report, or reports that no test change is warranted; in both cases the baton returns to coder. A semantic/invariant change goes to owner/replan. A changed revision preserves old revisions/evidence and reruns affected checks.
- Every kill target maps to one contract and one stable `TEST-ID` resolving to one exact nodeid. Only that test's assertion failure may yield `PROVEN`; unrelated test failure remains a separate suite failure. Collection/setup/skip/timeout/launch/runner/JUnit errors and zero executed tests classify as `ERROR`, never `PROVEN`.
- Seal/mapping integrity failures block in both `observe` and `enforce`. Determinate kill failures retain current mode behavior: advisory in `observe`, repair-blocking in `enforce`.
- Coder may add separately classified support/regression tests, but they cannot edit or replace sealed acceptance sources or become planner acceptance/kill oracles without a new planner revision.

**Artifact C is selected:** the new post-I03 plan schema owns semantic `CT → TEST-ID → selector` mapping; a controller-minted, versioned `AcceptanceBundle` binds it to an immutable workspace revision and the complete acceptance source/config/fixture/driver/runner closure, including exact selector→nodeid resolution. The authority must provide a visible mode-A read-only projection across shell and file tools, reject closure changes at seal/publication, and make verifier execute that same pinned revision/digest. If C cannot prove complete closure or read-only projection, fail closed and use B's separate immutable payload; never substitute a hash-only sidecar. The legacy v1 grammar itself is not a compatibility requirement.

The operator also selected three high-ROI controls for implementation: **Hollow-Facade protection** (real entry/composition plus authoritative effect/no-effect for durable/external claims), **sealed oracle closure** (including fixtures/drivers), and an **honest pre-code gate** (distinguish assertion sensitivity from collection/setup/runner failures; `NotImplementedError` alone is not sensitivity evidence).

### Concrete false-attribution case

A mutation is assigned to `CT-A`. Its intended oracle `test_a_contract` passes under the mutation, while an unrelated `test_b_auth` fails. Today the slice-wide JUnit `failure_count` can make the kill-check for `CT-A` `PROVEN`. The required new result is: `CT-A` is **not proven** (the mapped test survived, hence `VACUOUS` for the kill check); the independent suite failure remains recorded and keeps the overall suite result failing. A setup/collection error or timeout is `ERROR`, never `PROVEN`.

The target test's “unmutated pass” means a pass on the **current implementation immediately before applying the mutation**, after verification. It does not mean pre-coder T0: a newly authored behavior test may correctly be red before implementation.

## 4. Artifact-seam alternatives

| Criterion | A. Put mapping in the new plan schema | B. Separate versioned `AcceptanceBundle` | C. Hybrid: new schema + revision-bound seal |
|---|---|---|---|
| Representation | Put stable test IDs, exact selectors and CT/kill-target mapping directly in the forward-only plan grammar/schema used by new plans. This does not migrate, revise, or require compatibility with the archival current v1 plan. | A separate versioned artifact owns the acceptance contract, mapping, selectors, byte seal, visibility and run contract, linked to the new plan revision. | New schema is the semantic source for invariants and `CT → TEST-ID → target` mapping; a separate versioned seal/bundle binds that plan revision to test bytes, resolved selector/nodeid, visibility and execution evidence. Do not duplicate the semantic mapping as a second authority. |
| Example | New-schema plan declares `TEST-A → tests/test_a.py::test_a_contract` and assigns a particular kill target to `TEST-A`. | `acceptance-bundle.json` records `PlanRef`, `TEST-A`, the uniquely resolved nodeid, test-source closure/hash, runner and bundle revision. | Plan owns `CT-A → TEST-A`; the seal records plan digest, workspace revision, exact source closure digest, selector→nodeid resolution and effective mode, then evidence references both. |
| Custody | Schema can say who owns the test, but cannot itself make referenced bytes immutable. It still needs a controller seal and authority enforcement. | Clearest independent revision boundary; can store/copy test sources away from the coder's mutable tree. | Reuses immutable workspace revisions, but needs authority-enforced protected-path policy and a complete test-support/config closure. Hashing only the target `.py` is insufficient if fixtures, `conftest.py`, runner config or imported helpers can change behavior. |
| Exact attribution | Straightforward to express; result artifacts still need the exact expected and observed nodeid. | Natural place for target→contract→TEST-ID→nodeid and evidence binding. | The semantic map stays in one source; bundle/evidence bind the observed execution to it. |
| New-plan schema | Requires integrating the mapping into the new schema, but leaves old v1 archive-only. | New schema only needs a bundle reference; bundle can evolve independently. | New schema defines semantics; seal schema defines byte custody. The reference/hash prevents either side changing silently. |
| Future hidden mode B | Possible, but read/write access remains a separate concern. | Best fit for a verifier-only source provider, with the same bundle exposed read-only in A. | Also supports B if the seal references a source-provider interface, rather than exposing workspace paths directly. A thin manifest alone does not hide source bytes. |
| Main benefit | One normative schema and fewer artifacts. | Strongest single custody boundary and clear lifecycle. | Separates semantic ownership from byte custody without modifying legacy v1 or duplicating CT mapping. |
| Main cost/risk | Risks placing operational hashes/runner state into the plan schema and still needs an authority capability boundary. | Additional source storage/overlay/import lifecycle; avoid a second mutable source of truth. | Requires coordinated new-schema + seal schema and authority changes; full test-source dependency closure must be explicit. |

### Selected architecture — C with B-payload fallback

The operator selected **C as the storage strategy, with B's explicit `AcceptanceBundle` interface**. If the implementation cannot prove complete closure or a true read-only coder projection, fall back to B's separate immutable payload; do not weaken custody to a hash-only record.

1. The new post-I03 plan schema owns semantic expectations and the single mapping `kill target → CT → TEST-ID → selector`. This is forward-only; it does not modify/migrate the archival current v1 plan, and it avoids duplicating contract mapping in two authorities.
2. A controller-minted, versioned `AcceptanceBundle` is created before coder-stage. It binds the new plan digest to the exact test-source revision/complete closure, selector→nodeid resolution, effective visibility mode (A by default in W3), runner contract, and revision lineage. It is the byte-custody/execution envelope, not a second source of truth for invariants or target mapping.
3. W3 may let the bundle reference the existing immutable workspace revision, but only with new closure-aware enforcement: bind the accepted path closure to that revision, reject changed/added/deleted acceptance bytes at stage seal/publication, and expose the pinned closure through an actual read-only coder projection. The current final-seal check alone is not enough, and neither is `RootedViewIO.protected_paths`: writable coder cells receive the whole source tree at `/workspace` as a read-write mount. The new authority/container seam must cover both file-tool writes and shell access. This avoids duplicating the test tree only if the complete support/config closure and actual read-only mount can be proven; otherwise use pure B's isolated payload.
4. The same bundle/provider interface can support future hidden mode B without exposing implementation to coder. If the workspace-revision provider cannot guarantee the identical bytes to coder-visible A and verifier, fall back to a self-contained, immutable bundle payload rather than weakening custody.
5. `verification.json` binds every result to plan digest, bundle digest, target/TEST-ID, exact nodeid, source revision, baseline result, mutant result, and JUnit run. The mapped test must pass on the current unchanged implementation immediately before mutation; T0 may be red. Under mutation, suite status remains separate: only the mapped test's assertion failure proves the kill, and unrelated failures cannot substitute.

The artifact choice is ratified; implementation evidence is not. Pure A is not selected. Pure B is the mandatory fallback if C cannot provide complete closure integrity and strict mode-A read-only projection; a hash-only sidecar is never an acceptable substitute.

## 5. Proposed owner/capability handoff (design only)

| Boundary | Owner and artifact/capability | Required authority check |
|---|---|---|
| Plan authoring | Planner authors the invariant, contract IDs, stable `TEST-ID`s, selectors and one-target/one-test mapping in a new-schema plan revision. | Admission validates uniqueness and complete mappings; the plan revision is pinned, not inferred from a mutable path. |
| Acceptance seal | Planner/controller requests a versioned bundle seal against the admitted plan and immutable workspace revision. The authority mints the seal/bundle identity; caller-provided hashes are not accepted as proof. The closure includes test bodies, fixtures, scenario drivers, assertion/oracle helpers, test configuration and runner contract. | Recompute the complete declared closure, resolve every selector to exactly one stable nodeid, bind runner configuration and visibility mode, and record the plan/revision identities. Missing/ambiguous closure or selector is a hard error. |
| Coder stage | Controller opens code-edit capability plus mode-A read access to the pinned acceptance source. The coder gets no seal/update capability. Support/regression test writes are separately classified. | Do not rely on prompt policy or `RootedViewIO.protected_paths` alone: the visible acceptance projection must be read-only through both file tools and shell, and publication must reject changes to the sealed closure. An explicit mode B request before support returns `UNSUPPORTED` and does not open an A view. |
| Verification and mutation | Verifier receives a read-only pin to the bundle/source revision and a separate mutation execution capability for code. | Recheck bundle bytes and mapping at the execution boundary; run the mapped test on current unmutated code immediately before the mutation, then attribute only that exact nodeid's assertion outcome. The verifier cannot change the plan or bundle. |
| `TEST-DEFECT` disposition | Coder reports the defect against invariant, bundle revision/hash, `TEST-ID`/nodeid and assertion. Planner either leaves it unchanged with a disposition or produces a new plan/bundle revision; owner handles semantic changes. Both planner outcomes hand the baton back to coder. | The old revision and evidence remain immutable. Any new acceptance revision gets a new seal and reruns affected gates; no in-place update, no silent remap, no acceptance credit for coder-authored support tests. |

This division places semantic authorship with the planner, byte custody with the authority, implementation edits with the coder, and verdict production with the verifier. It is a proposed minimum capability split; current stage roles/capabilities do not yet implement it.

## 6. Required execution/evidence flow

1. Planner authors the acceptance tests and mapping before coder-stage. For durable/external-effect claims, tests traverse the real production entry/composition and assert the source-grounded authoritative effect, or assert no durable effect on refusal; this is claim-specific and does not mandate a database assertion for every test. Admission binds a seal to the new plan and precise test-source revision; missing or ambiguous identity is a hard error.
2. Before coder-stage, a deterministic pre-code gate validates syntax, imports, collection, fixture/setup and runner. It separates assertion outcomes from infrastructure errors. A test claimed sensitive to a new behavior must fail by its mapped assertion on a scenario-specific null/no-op or known-bad witness when one is applicable; `NotImplementedError`, setup failure, skip or zero executions do not demonstrate sensitivity. Preservation tests can already pass, and no new-behavior test is required to be green on pre-coder T0.
3. In W3 mode A, coder can inspect the sealed source but cannot publish changes to accepted bytes. Any coder-authored support tests remain a separate evidence class.
4. Immediately before mutation, the verifier runs the mapped test against the current unchanged implementation and requires that exact nodeid to pass; this is not the pre-coder T0 baseline. Against the mutation, it may execute the mapped test alone or the broader acceptance suite, but retains per-nodeid evidence and an independent suite verdict.
5. `PROVEN` requires a current, valid JUnit report for the exact expected nodeid and an assertion failure in that nodeid's test-call phase. A passing mapped test is `VACUOUS`; a skipped/missing mapped nodeid, collection/setup/timeout/launch/runner/JUnit error, zero executed tests, or a non-assertion failure is `ERROR`, never `PROVEN`. A failing unrelated suite test is never kill evidence and still leaves the overall suite failing.
6. Persist plan identity, bundle/seal hash, test-source revision/hash, mutation target, contract ID, TEST-ID, expected and observed nodeid, runner/command, baseline outcome, mutant outcome, and JUnit run identity in evidence.
7. On `TEST-DEFECT`, keep the sealed revision immutable. A planner correction produces a new revision and report, preserves old evidence, and reruns affected checks; no correction produces a disposition report and returns to coder. A semantic change routes to owner/replan.
8. A missing/stale seal, changed acceptance bytes or ambiguous mapping blocks even in `observe`. For determinate test/kill failures, existing `observe` remains advisory and `enforce` continues to route to repair.
