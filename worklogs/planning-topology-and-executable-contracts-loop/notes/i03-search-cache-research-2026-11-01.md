# I03: ресерч безопасного поиска по управляемому виду

**Статус:** рекомендация принята оператором по Q105, 2026-11-01. Не production-приёмка и не
закрытие STEP2b/W1. Прототип в рабочем дереве не подключён к агенту. Источники и измерения
ниже отделены от выводов; целевой Docker-host и Python 3.13 здесь не проверены.

## Желаемое поведение и границы

`fs_search` и `fs_reach` должны использовать те же алгоритмы и схемы, что сейчас, читать
**конкретный** управляемый view (открытый writer видит свои текущие изменения; pinned reader —
свою ревизию), возвращать обычный `ToolResult`, не менять исходное дерево индексом и не читать
канонический host root. Результат cell — данные, а не доказательство supervisor; capability,
идентичность и исход операции остаются у существующей authority. Отказ/timeout/truncation не
превращается в host fallback. Полный Q97 также требует PDF, telemetry, subagent и остальные
инструменты — данный документ закрывает только выбор для поисковых индексов.

Исходная spec §4.2 предписывала SQLite внутри per-view `/scratch`; после принятия Q105
она обновлена на одноразовый memory-index. При осмотре
`execution/profiles.py` обнаружено, что `/scratch` доступен shell и helper под одним uid.
Локальный проверенный контрпример: `search.db` или `structural.db` — symlink на файл в дереве
вида; существующий SQLite создал и записал файл через ссылку. SQLite также использует отдельные
journal/WAL/SHM имена; нормализация пути или предварительный `lstat` не защищают от подмены
после проверки. Реальный опубликованный разбор аналогичного класса с `/proc/self/fd` и sidecar:
[3](https://github.com/advisories/GHSA-v4x8-3wr5-3wq8). Это не утверждение о присутствии
уязвимого пакета filelock в проекте: релевантен класс ошибки.

## Факты ресерча и кода

- Официальная SQLite: `:memory:` приватна соединению; `mode=memory&cache=shared` связывает
  соединения **в одном процессе**, память освобождается при закрытии последнего соединения
  [1](https://www.sqlite.org/inmemorydb.html). Общий SQLite shared-cache в общем случае
  не рекомендуется и может отсутствовать в сборке [1](https://www.sqlite.org/sharedcache.html).
  Поэтому использовать его только локально, не считать межпроцессным кешем и явно проверять
  поведение целевой SQLite; альтернатива — один соединённый lifecycle внутри StructuralIndex,
  но её ещё нужно реализовать и проверить на конкурентность/cleanup.
- `SearchIndex` держит своё соединение, а `StructuralIndex` открывает короткие соединения для
  build/lookup/reachable (`memory/structural_index.py`). Наивное подставление `:memory:` в
  каждый `_connect` создаёт разные пустые базы: локальный мутант приводит к `no such table`.
- Python sqlite3 не предоставляет в сигнатуре `connect()` прямой аргумент C-флагов; SQLite
  поддерживает `SQLITE_OPEN_NOFOLLOW` на C-уровне [1](https://www.sqlite.org/c3ref/open.html),
  но открытие только основной БД не доказывает безопасность sidecars, same-uid подмены и
  корректность восстановления. Не вводить `ctypes`/свой VFS как «простую проверку».
- SQLite рекомендует обращаться с БД, которые мог изменить другой домен, как с недоверенными:
  `trusted_schema`, ограничения и проверка целостности — дополнительные меры
  [1](https://www.sqlite.org/security.html), **не доказательство**, что содержимое индекса
  соответствует дереву. Поэтому snapshot SQLite в общем scratch с `serialize`/`deserialize`
  и безопасным `openat` может защитить размещение, но не защищает от поддельных/устаревших
  ответов и добавляет недоверенный парсер, лимиты, lifecycle и дополнительные копии. Не выбран.
- В коде `WorkspaceAuthority.admit` разрешает **один** `approved_profile` и выдаёт один
  подтверждённый source/scratch/cache triple на view; `CellBackend` владеет одной живой
  interactive episode и выдаёт её текущей проверке остановки. Второй index-only cell с закрытым
  scratch — возможная более сильная изоляция, но сейчас не существующий стык: нужны отдельное
  подтверждённое хранилище, профиль/адмиссия, запрет произвольных shell-команд к index cell,
  учёт нескольких контейнеров в stop/drain/recovery и реальные host-доказательства. Нельзя
  просто подставить второй путь или выбрать другой профиль в запросе. Это изменение границы,
  а не маленькая оптимизация.
- Долгоживущий helper/coprocess с in-memory DB снимает повторную сборку, но требует отдельного
  протокола/жизненного цикла, управления сбоями, PTY pool и гарантированного останова
  потомков. Имя PTY и его состояние не являются authority, другие команды могут его сломать;
  нельзя подменять неопределённый ответ автоматическим повтором. Не добавлять эту службу ради
  неподтверждённой оптимизации.

## Результаты локального эксперимента

Процессы запускались отдельно в Python 3.11+shim, индексы disk сохранялись в одной временной
директории; время измерено внутри процесса, запуск интерпретатора и Docker сюда не включены.
Срез `src/fa`: 198 Python-файлов, три вызова каждого инструмента.

| Инструмент | in-memory, каждая перестройка | disk cold / два warm | peak RSS |
|---|---:|---:|---:|
| search | 0,589 / 0,570 / 0,668 с | 0,875 / 0,022 / 0,027 с | memory ~44 МиБ, disk warm ~30 МиБ |
| reach | 0,906 / 0,851 / 0,699 с | 0,955 / 0,020 / 0,019 с | memory ~38 МиБ, disk warm ~27 МиБ |

Синтетический каталог из 1000 небольших Python-файлов (4 МиБ на диске), по два отдельных
процесса: search memory 0,634/0,778 с vs disk 0,937/0,056 с; reach memory 0,531/0,620 с vs
disk 0,631/0,037 с. Кеш обоих индексов ~6,2 МиБ. Форма и содержание синтетики не заменяют
реальные большие репозитории и являются **не порогом** приемлемости. Peak RSS — всего процесса,
не только SQLite. Три/два замера без статистической оценки и конкурирующей рабочей нагрузки.

Прототип: 24 локальных теста (семантика сравнена с disk для выбранных примеров, предыдущие две
symlink-атаки и конкурентная подмена); 13 целевых call-phase mutants. Это не доказательство
полного Q97, fairness, всех гонок, ограничения памяти, или работы на реальном host.

## Рекомендация

**Для текущего I03 выбрать одноразовый memory-index как безопасную исходную архитектуру, а не
добавлять новый сервис или привилегированную границу до появления доказанной необходимости.**
Тонкий helper запускается через существующий EXEC с `/workspace`, строит in-memory индекс с
`temp_store=MEMORY`, отвечает ограниченным envelope, завершается. Каждый запуск привязан к
уже разрешённому view и его cell; временный индекс не переходит между pin/view и не проходит
через доверенные host пути. Legacy disk-инструменты остаются без изменений; search/reach
переиспользуют существующую реализацию. До интеграции убрать/исправить дефекты прототипа,
проверить schema, duplicate keys, output bounds, attribution и error mapping на стыке.

Это **конкретное отклонение** от текущего текста §4.2: scratch по-прежнему нужен для среды
cell, но индекс не сохраняется там между вызовами. Оператор принял эту рекомендацию; изменение отражено в §4.2 спецификации. Q97 не понижается: если реальный host
покажет неприемлемые затраты или не удастся обеспечить явный bounded отказ при нехватке
памяти/времени, W1/production не закрывать. Не придумывать численный SLO задним числом.
Отдельный защищённый cache — следующий кандидат только при подтверждённой необходимости;
его новые границы и изменение контрактов требуют отдельного плана и Q, а не скрытого fallback.

## Условия, без которых это не production

1. Реальный host с target Python/SQLite и утверждёнными cgroup/seccomp/image: проверка
   работоспособности FTS5, shared cache (либо альтернативы), resource limits и cleanup.
2. Замеры холодного и повторного поиска на маленьком, типичном и большом реальном workspace,
   несколько вызовов с конкурентной shell-нагрузкой и сравнением disk baseline; зафиксировать
   реальные допустимые бюджеты до вынесения вердикта.
3. Большие файлы/число файлов/индекс исчерпали лимит, сигналы/OOM/timeout/truncated output,
   backend unavailable/uncertain — отсутствие частичного успеха и host retry, проверка
   дальнейшей жизнеспособности cell и необходимости recovery.
4. Параметры/paths, active и pinned view, shell edits, symlink/hardlink/sidecar races,
   crash/restart/stop, атрибуция в `SessionState`, PDF и legacy parity по owning tests.
5. Финальная проверка обоих сценариев фабрики, W1/W2/W3/W4 и всех host acceptance rows;
   после STEP2b — type gates по Q103, до закрытия W1.
