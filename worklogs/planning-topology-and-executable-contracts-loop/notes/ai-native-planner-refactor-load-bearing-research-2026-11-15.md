Recommended artifact model:

1. **Markdown is the canonical authoring source** for new plans. A versioned parser/validator turns it into a typed, validated machine representation; that representation is a projection, not a second semantic authority.
2. The plan owns stable semantic identities and links: invariant → `CT` acceptance obligation → `TEST-ID` → exact selector, plus any applicable kill/target attribution. 3. The controller-minted `AcceptanceBundle` binds the admitted plan revision to exact acceptance bytes, configuration, fixtures, helpers, driver, runner, selector→nodeid resolution, and workspace revision. It is custody/execution evidence, not a second mapping database.
4. Planner authors acceptance before coder; the controller/authority admits and mints its seal/bundle. Coder sees the accepted source read-only (the ratified mode A); code and coder-added support tests are separate from planner-owned acceptance. Eval/harness runs the pinned, exact gates and reports machine facts separately from any judgment.
5. The planner should fully resolve the **accepted invariants and the relevant behavior/edge matrix** before implementation. That does not require prescribing every future file, class, or work-order. Fully map outcomes and dependencies now; make the nearest vertical slice executable in detailed steps; keep distant implementation steps at rolling-wave outline.
6. Do not require a planner approval round-trip for every coder-selected seam. Coder owns implementation choices within the admitted behavioral, safety, and ownership boundaries. A concise coder-owned seam trace may help evaluation, but should be optional unless needed to support a specific invariant/evidence claim. Record semantic ambiguity as a Q; the planner may make a best-effort decision with a short rationale. Do not silently rewrite a ratified increment invariant/non-goal to make a choice fit; if that requires change, flag the affected scope for replan/ASK and continue unrelated work. Whether to add a later risk-gated architecture review remains open.

A key mismatch already exists in the current documents: the roadmap says the planner authors each slice's test, while the current artifact schema assigns repo code **and tests** to coder. The new model is a deliberate change in role ownership, not a wording-only update. It must be reflected consistently in the new schema, parser/validator, write capabilities, stage transitions, prompts/skills, and tests.

## 4. Reconciled planning model

### 4.1 Planning layers

A plan should distinguish four different things rather than treating them all as “steps”:

1. **Owner intent and risk boundary:** desired result, users, external systems, non-goals, acceptable risk, irreversible choices, and decisions that must be asked. Research is evidence for choices, not authority to make product decisions.
2. **System/feature invariants:** stable, observable, implementation-independent claims. Each has an ID, scope, source/authority, observable boundary, and explicit conditions/exceptions. If classification is used, keep independent axes separate: obligation kind (e.g. behavior/constraint/preservation), enforcement/criticality (e.g. blocking/advisory), and risk tier. Do not compress them into one ambiguous enum. No class/method name belongs in an invariant unless that identity is itself an external contract/security boundary.
3. **Acceptance scenarios and tests:** scenarios bind the accepted behavior to exact expected observations and tests. Include positive, refusal/boundary, preservation where material, and relevant failure/recovery cases. Use property/stateful/mutation/integration evidence where the claim requires it; do not rely on a prose claim or test count as proof.
4. **Vertical slices and coder work orders:** slice is a runnable, observable outcome through the production path. Detailed implementation steps are short-lived work orders; they are not the authority for product semantics.

This is compatible with “full decomposition” if full means all required outcomes, invariant owners, risk boundaries, and dependency relationships are mapped. It is not compatible if full means every future private module, method, or implementation step is fixed up front.

### 4.2 Operator-selected identity/mapping model; remaining relation details are open

The operator selected `INV + CT + TEST`, with `SCN` optional. This is the intended **new-schema semantic model**, not support for the old grammar:

- `INV-ID`: cross-scenario/system property that must remain true.
- `CT-ID`: one atomic, externally observable acceptance obligation at a boundary/slice. It is not another spelling of an invariant and does not carry the entire system-level claim.
- `SCN-ID`: optional, formal scenario artifact for a concrete user path/journey. It captures the actor/context, preconditions, action sequence, observable outcomes and relevant failure paths; analysis of it helps the planner derive/refine invariants and atomic CTs. Its explicit relation is `SCN → CT-ID[]`; associated TEST-IDs are derived through CT→TEST. SCN supplies behavioral context but does not replace the normative claims in INV/CT or the executable oracles in TEST.
- `TEST-ID`: stable identity for a planner-authored executable oracle, with an exact selector that resolves to exactly one collected nodeid in the pinned closure; each parametrized case has a stable explicit case id and its own TEST-ID.

Confirmed cardinalities: one INV may have multiple CTs; every CT has exactly one primary INV; a CT may have multiple TESTs; each TEST-ID belongs to exactly one CT and resolves to exactly one collected nodeid. Optional SCN is a formal scenario/path artifact that gives the planner behavioral context for deriving/refining precise invariant and contract obligations; it explicitly links `CT-ID[]`, and its TEST set is derived through CT→TEST. STEP9A's mutation attribution remains stricter and separate: each kill target maps to exactly one CT and one TEST-ID/nodeid. Adding INV does not replace CT in that target-level attribution, and keeping CT as an ID namespace does not preserve or enable the old plan parser.

The operator resolved the key graph cardinalities and links: one CT has exactly one primary INV; INV may fan out to many CTs; a CT may have many TEST-IDs; each TEST-ID belongs to one CT and resolves to one collected nodeid; optional SCN is a formal scenario linked to `CT-ID[]`, and its TESTs derive through those CTs. Still to specify before schema freeze: how an invariant whose claim has no direct executable test records its evidence/sign-off, and whether every CT is required to have at least one executable TEST-ID or may declare a different evidence disposition. Recommendation: every executable CT has at least one planner-authored TEST-ID (or an explicit non-executable evidence disposition), while each kill target resolves to exactly one declared CT/TEST/nodeid.

To avoid two competing membership authorities, the operator selected `SCN → CT-ID[]`; the SCN's TEST set is derived through CT→TEST. Do not store a second direct TEST-ID list under SCN. The scenario itself is a formal analysis artifact: its actor/context, preconditions, action sequence, expected observations and failure paths help the planner derive or refine invariant/contract obligations, while its explicit CT-ID array keeps the executable-contract graph normalized.

#### INV↔CT cardinality: worked example and recommendation

Assume a greenfield business site plus an integration to the business's existing CRM. Product choices such as which fields are collected, consent wording, and CRM-outage behavior are currently open questions; under the selected autonomy policy, the planner may choose and record best-effort resolutions, provided it does not silently rewrite a ratified increment invariant. The examples below describe candidate boundaries, not settled requirements.

- `INV-WEB`: the visitor-facing site exposes owner-approved business information and a usable inquiry path.
- `INV-CRM`: an accepted inquiry is transferred to the existing CRM accurately and without duplicate creation on retry.
- Plausible CTs: `CT-WEB-PAGES` (required pages render with the agreed content), `CT-WEB-INQUIRY` (valid/invalid inquiry behavior is observable), `CT-CRM-MAP` (agreed form fields map to the authoritative CRM record), `CT-CRM-IDEMPOTENCY` (retry does not create a second record), and—after Q resolution—`CT-CRM-UNAVAILABLE` (outage produces the agreed honest/recoverable outcome).

| Model | What it means in this example | Advantages | Costs / failure modes | Assessment |
|---|---|---|---|---|
| Strict one-to-one | Exactly one CT per INV and exactly one INV per CT. The site invariant and CRM invariant each get one CT. | Small mapping; easy to validate. | Each CT becomes a broad bundle of pages, forms, CRM mapping, retries, and outages; hard to make atomic or assign one exact oracle. Splitting the invariants into one-per-obligation would distort the intended cross-scenario meaning of INV. | **Reject for this model.** It defeats the selected distinction between durable invariants and atomic acceptance obligations. |
| One-to-many hierarchy | One INV may own several CTs; each CT has exactly one primary parent INV. Site and CRM invariants each fan out to focused CTs. | Clear completeness and ownership; tests and mutation attribution stay local; no many-to-many coverage ambiguity. | A cross-cutting behavior needs an explicit owner/parent choice and may need more than one focused test/CT; a whole user journey must be represented as a scenario/group rather than a CT claimed by several parents. | **Operator selected for MVP.** Preserve `INV → many CT`; every CT names exactly one primary INV. |
| Many-to-many | A CT can be linked to multiple INVs, e.g. one end-to-end form→CRM CT claims both `INV-WEB` and `INV-CRM`. | Captures genuinely cross-cutting obligations without duplicating the contract; concise for integrated journeys. | The same CT may falsely appear to complete two invariants while asserting only one side; validator needs per-INV evidence/coverage, and mutation/evidence disposition must say which claim failed. “CT is atomic” becomes harder to maintain. | Not selected for MVP. Optional scenario grouping can express a cross-cutting journey without multi-parent CT ownership. |

Under the selected hierarchy, a formal `SCN` describes a shared journey and explicitly links its focused CTs, while each CT and its TEST-ID retain one owner. The scenario helps derive/refine obligations; its TEST set is derived from CT links. This is intentionally different from saying the same CT/test proves both invariants. I recommend that no single acceptance test be counted as satisfying two CTs by implication; if a journey asserts two independently meaningful obligations, give each obligation its own focused TEST-ID/oracle, potentially sharing setup/fixtures but not kill attribution.

#### TEST-ID↔nodeid cardinality (adversarial edge case)

The current bundle design requires selectors to resolve uniquely, and STEP9A requires an exact nodeid for each kill. Pytest parameterization is the edge case: one source-level selector may collect many concrete nodeids.

| Model | Advantages | Costs / failure modes | Assessment |
|---|---|---|---|
| One TEST-ID → exactly one collected nodeid | Exact attribution, stable per-case evidence, simple seal and negative controls. Parameter cases receive distinct TEST-IDs and explicit stable pytest parameter IDs. | More IDs and plan rows; changing parameter IDs is a schema/evidence change. | **Operator selected for MVP.** Reject selectors that resolve to zero or multiple nodeids; model a parameter case as its own TEST-ID. |
| One logical TEST-ID → multiple nodeids | Natural for a parameterized test family and concise plans. | A kill can be caused by one parameter while another passes; target-level mapping then needs a child-case identity or explicit selected nodeid, plus per-nodeid result semantics. Without that extra layer it violates the one-target→one-TEST/nodeid rule. | Defer unless real authoring cost justifies a separate `CASE-ID`/child selector design. |
| Disallow parameterized acceptance tests | Smallest validator and no nodeid expansion. | Restricts ordinary pytest idioms and can encourage copy-pasted tests. | Unnecessary if IDs can be assigned to concrete collected cases. |

The operator selected one `TEST-ID` → exactly one nodeid as the MVP rule. Pytest parameterization is allowed only when every case has a stable explicit id and its own TEST-ID. This preserves strict STEP9A attribution without banning parameterization; changing a collected nodeid is an acceptance mapping revision, not a silent refactor.

The plan should state for each acceptance claim:

- invariant/scenario IDs and source of expected semantics;
- user-visible input and observable result/effect, or explicit no-effect on refusal;
- test ID, exact selector, and test class (new behavior, preservation, property, composition, etc.);
- whether it is expected to fail before implementation or may already pass;
- what assertion/oracle constitutes the evidence and what setup/collection/runner outcomes are `ERROR`, not acceptance;
- required production path and authoritative sink for durable/external-effect claims.

The AcceptanceBundle should carry execution/custody identity: admitted plan revision/digest, immutable workspace revision, complete test/support/config/fixture/driver/runner closure, effective visibility mode, selector→nodeid resolution, and result lineage. It must not create a second mutable copy of invariant/test semantics.

### 4.3 `open-questions.md` is a required root artifact (operator-selected)

The operator selected a required `open-questions.md` in each new-format project root beside `roadmap.md` and `ledger.md`, and explicitly authorized the planner to write and resolve questions, including product-policy questions, autonomously on a best-effort basis. This is delegated decision authority, not merely clerical write access. The durable boundary is the active increment's ratified invariants/non-goals: the planner must not silently rewrite them through a Q resolution. If a choice requires changing a ratified invariant or the invariant cannot be met, record the Q/ASK and replan only the dependent scope; unrelated work should continue. Keep the root file scoped to this project's active questions and link to repository-wide questions rather than copying the existing large tracker/history.

The plan validator should prevent only a dependent slice from being marked ready when a truly blocking Q remains unresolved; unrelated slices/work should proceed. Resolution needs a recorded choice and short rationale, but should not turn the tracker into a heavyweight approval workflow. Exact status vocabulary and the current best-effort ASK behavior remain to be planned; future interactive `ask_user` support is not an MVP dependency.

### 4.4 Where test files belong

The decision that test files are outside the plan is sound. The exact directory is **not yet settled** and should not be selected for convenience alone. Before choosing it, source-ground:

- how the production verifier discovers and runs tests from a newly created project;
- import/config behavior and the trusted working directory;
- how IDs/selectors resolve uniquely and remain stable enough for evidence;
- how fixtures, helper modules, plugins, config, test drivers, and runner versions are included in the sealed closure;
- whether files live in the project workspace revision, a separate immutable payload, or another already-supported authority path;
- how coder sees the files read-only through both shell and file tools while the verifier executes the same bytes.

Preferred principle: keep the authored plan human-readable and concise; keep test code separately executable and visibly linked; put the whole closure under one controller-minted identity; never rely on a hand-maintained hash sidecar or prompt-only read-only instruction. Reuse the existing workspace revision/provider and verifier seams if their contracts can prove this end to end. If not, use the already ratified isolated immutable-payload storage fallback rather than weakening custody; this is distinct from visibility mode B.

## 5. Coder seam autonomy: recommendation and trade-off

### 5.1 Recommendation: no mandatory planner approval after every seam proposal

I agree with the user's concern that a mandatory `coder → planner → coder` cycle on every implementation seam may add cost without reliably improving design. A routine implementation choice—module boundary, private function, internal protocol—should not need owner approval if it preserves the admitted invariants and acceptance.

The coder can reason about and implement seams in one coder stage. If a compact seam note is required, make it part of the coder's own work product, not a separate model dispatch or a universal approval gate. It can record the production entry→producer→consumer→observable result, ownership of state/effects, failure boundary, and what remains intentionally MVP. The purpose is traceability and evaluation, not an invitation for the planner to prescribe private structure.

### 5.2 What must not be lost by removing that handoff

Acceptance tests prove behavior only to the degree that their oracle is real and their path is composed. They do not automatically prove the code has clean seams, and visible tests can still be satisfied by an over-coupled implementation. This project's Q90 history records component tests that missed an absent production caller. Therefore:

- require acceptance for key behavior to traverse the real production entry/composition, not just a new helper;
- have eval/harness check applicable producer/caller/EDGE evidence and authoritative effect/no-effect;
- retain typed failure paths (`PLAN-GAP`, `TEST-DEFECT`, `ASK`/replan) rather than letting coder weaken acceptance;
- let planner resolve ordinary product-policy Qs within the accepted plan; a change to a ratified invariant/non-goal requires replan, and unresolved security/data-authority conflicts block only the dependent scope;
- do not require approval for ordinary internal implementation choices.

A future risk-gated independent architecture review may be worthwhile for security, durable data, external APIs, migrations, or irreversible effects. That is a separate policy decision and should not be silently added to the MVP. A review can also be conditional on a concrete signal (unmapped effect, changed ownership, boundary crossing) rather than a universal extra turn.

### 5.3 Important distinction: planner review on `TEST-DEFECT` is conditional

STEP9A's `TEST-DEFECT` flow is not the same as reviewing every coder seam. It is a bounded exception path: coder reports a specific defect in a sealed test; planner either issues a new sealed revision with rationale or leaves the test unchanged with a disposition; a semantic change routes to owner/replan. Old bytes and evidence remain. Keep this because otherwise the coder can silently redefine the exam, but do not turn it into a mandatory approval stage on every ordinary implementation pass.

## 6. Full detail versus hyper-planning

The user is right that accepted invariants and important edge cases should be settled before coder implementation. That is where excessive control prevents agents from inventing business semantics or crossing safety boundaries. The limit should be **semantic completeness**, not document length or implementation completeness.

Recommended planning depth:

- **Fully specify now:** scope/non-goals; accepted invariants; owner/source for expected behavior; observable boundary; important negative/no-effect behavior; privacy/permission/data ownership; retry/cancellation/unknown outcome where applicable; compatibility/migration/rollback where applicable; blocking questions; test oracle and evidence type; dependency order.
- **Use matrices/properties instead of endless examples:** enumerate important state transitions and classes of inputs; test representative/known edge cases and use property/stateful generation where the invariant is universal. “Maximum edge exploration” is not a proof that every edge was listed.
- **Do not fix prematurely:** every module/class/file, all far-future STEP commands, optimization and general abstractions, or implementation routes that the seam proposal is meant to let coder discover.
- **Make every proposed slice semantically executable; make only the nearest coder work order step-by-step executable.** For all proposed slices, specify behavior, invariant/CT/test mapping, oracle and edge/failure cases, dependencies, and local/host DoD/exit criteria. Apply rolling-wave detail only to later implementation steps, internal file/module choices, and execution sequencing that can be refined without changing accepted behavior. If an invariant spans future slices, map its applicability and evidence to each relevant slice now without freezing internal construction.

This is not an argument for vague planning. It is a way to spend precision where agent error is costly—semantics, ownership, effects, and oracle—and preserve coder autonomy where a design choice can be changed cheaply.

### 12.4 Harness-owned bootstrap assessment and decisions before planning

**Assessment.** This is a strong architectural fit. It moves deterministic structure, naming/path safety, version stamping, file rendering, and admission sequencing into the trusted layer, where they can be deterministic and testable. Important nuance: current V1 already has the controller render/install the directory bundle; the planner returns a slug and roadmap/increment prose rather than doing raw `mkdir`/file writes. It also makes `invoke_workflow` a natural user-facing operation: one task/slug request, one controlled lifecycle, and a structured result. The main cost is not the renderer/parser alone; it is redesigning the current immediate bootstrap/admission into a multi-phase transaction with provisional state, bounded planner authoring, whole-project validation, seal, and recovery. That additional work is justified if the controller remains the sole materializer/authority and no provisional plan can reach coder.

**Responsibility boundary (selected direction).** Harness creates the project path and canonical V2 skeleton, version marker, and fixed required files. Planner supplies the project's semantics—roadmap/increment intent, `open-questions.md` decisions, formal SCNs and CT/INV contracts, plus acceptance/test-support closure—but should not have to mkdir/write boilerplate. Prefer the current pattern where a model supplies typed content and trusted publication code renders files; avoid widening planner filesystem capability merely to call the step “planner-write.” This preserves planner autonomy over decisions while removing clerical bootstrap.

**Small external API, strict internal validator.** A `pass/fail + code + text` tool response is a good caller contract, not a reason to make V2 validation shallow. Internally validate the canonical version, exact required artifacts, Markdown grammar, stable IDs/edges, selector→nodeid resolution, and sealed support closure. Codes should be stable/machine-readable; text should tell the agent what to repair without exposing host paths/secrets. Retryability must distinguish correctable content from collisions, unsupported schema, and uncertain write/install state. Existing `invoke_workflow` has structured failure results, but normal pipeline exits are currently returned as `{exit_code,status}`; STEP9B must test the desired bootstrap-specific error mapping through the actual chat tool caller.

**Lifecycle to design and prove:** `NEW → SCAFFOLDED → PLANNER_CONTENT_READY → VALIDATED → SEALED/ADMITTED`. Every transition is controller-owned and tied to managed workspace revisions. Only `SEALED/ADMITTED` is visible to coder. Define crash/retry behavior, slug collision refusal/no-overwrite, and cleanup or resumability of provisional projects. Do not make an uncertain install look like a clean retry. The new flow must reject legacy V1 after cutover and have no compatibility fallback.

### 12.7 Remaining policy/detail questions

- Define the evidence disposition for an invariant or CT that cannot/should not have a direct executable test, and require all hard invariants/ready CTs to be covered or explicitly dispositioned.
- Define minimal `open-questions.md` fields/statuses and best-effort ASK behavior without imposing a heavyweight approval workflow. Keep active project questions scoped, link rather than duplicate the large repository tracker, and block only dependent work.
- Source-ground whether planner-authored V2 content can stay in private staged payload and be atomically materialized only after validation; the selected invariant is validate/seal before coder, not exposure of a provisional canonical directory.
- Source-ground how the trusted harness uses the sole canonical V2 grammar to render a fresh project skeleton, what explicit version marker it writes, and how admission validates it without letting project content choose the grammar.
- Production acceptance must prove harness-owned status ticks for V2 artifacts. No V1 status bridge or migration is needed for Arena authoring.
- Exact V2 test directory and support closure remain open; source audit found the existing managed pytest runner and no current basis for a parallel runner. Prove new admission uses the read-only managed path with no host fallback.
- Held-out eval tests are not an MVP requirement under the operator's mode-A decision; retain them as a future independent evaluation option and document the residual planner-blind-spot risk.
