## 0. Метод: сначала желаемое поведение, потом код

Правило разбора для каждого дефекта:

1. **Желаемое поведение модуля** — одно предложение, что этот модуль обязан гарантировать.
2. **Что код делает сейчас** — с точной ссылкой.
3. **Вердикт** — реальный дефект / ложная тревога / неверная постановка.
4. **Фикс** — и главный вопрос: *удаляем или добавляем?* Если для исправления нужно
   добавить больше, чем удалить, — почти всегда неверно поставлена задача.
5. **Закрывает ли класс** — а не один экземпляр.

Почему так: группа дефектов Q90 — не набор независимых багов. Это **один случай
несовпадения модели**: подсистема `execution` написана как «единственный писатель
снимками», а первый её production-потребитель (публикация плана) — «патч одного файла».
Отсюда почти все симптомы. Поэтому лечение «по одному багу» даст 15 заплаток, а лечение
по классам — три удаления и две маленькие правки.

Аналогия, которая объясняет всё дальше:

```text
Снимок (sealed publish):   «замени ВЕСЬ мир версией X, если мир всё ещё версия B».
                           Здесь CAS на base_revision обязателен: иначе тихо откатишь
                           чужие правки.

Патч (plan publish):       «замени ОДИН файл на такие байты, если там всё ещё старые».
                           Здесь работают два факта: old_sha256 файла и дерево-результат.
                           CAS на base_revision не нужен — он ложно конфликтует с
                           любой посторонней публикацией.
```

`publish_view` (снимок) и `publish_candidate_plan` (патч) — разные операции с разными
предусловиями. В E273 плановый путь унаследовал предусловия снимка (R6: равенство базы).
Именно это — корень половины списка.

## 3. По каждому дефекту

### Класс A — «снимок вместо патча»

#### D1. Publisher кэширует `base_revision`

**Желаемое поведение.** Publisher ничего не помнит о состоянии workspace. Он переводит
«валидированный снапшот → PlanRef» и получает все факты от супервизора в ответе.

**Сейчас.** `self._base_revision = base_revision` (`client.py:179`), обновляется только
своим успешным publish (`:266`) и уходит в `CREATE_VIEW.base_revision` (`:205`).

**Почему это ломается в первом же прогоне.** Пока кодер работает, прод-путь публикует
чекпойнты; каждая такая публикация двигает `current`. К моменту ремонта плана кэш
устарел, `create_view` сравнивает его с `current` (`workspace.py:1932`) и отбивает
`STALE_REVISION`. То есть «repair» не работает ровно в том сценарии, ради которого он есть.

**Фикс.** Кэш удалить. База — то, что вернул супервизор, а не то, что помнит клиент.

#### D2. «Получить текущую ревизию» нечем

**Желаемое поведение.** Любой участник, имеющий право писать, может узнать голову
workspace, не забирая его себе.

**Сейчас.** Единственные ответы с `revision_id` — `REGISTER_WORKSPACE`, `ACQUIRE_WRITER`,
`HANDOFF` (`_OWNER_REPLY` в `protocol.py:153`). Первый отдаёт ревизию на момент регистрации,
два других **мутируют** (новая генерация, старый грант умирает). Read-операции
(`PIN_READER`, `CREATE_VIEW`) требуют `revision_id` на входе.

**Следствие для Q90:** фраза «obtains the current run-scoped grant/revision» в опции 1
описывает шаг, которого нет. Не «дорого», а **невозможно** без изменения провода.

**Фикс.** Не добавлять операцию. `CREATE_VIEW.base_revision` → nullable, `null` значит
«пин на текущую»: сервер уже это умеет (`workspace.py:1911` — параметр по умолчанию
`None`, проверка `:1932` уже под `if base_revision is not None`). Запрет живёт только в
схеме (`protocol.py:100`). Одно слово в схеме + один `_nullable`.

#### D3. R6 — не защита, а ложный конфликт

**Желаемое поведение планового коммита.** «Замени ровно этот файл, если в нём всё ещё
те самые байты, что я валидировал».

**Сейчас.** Плановый путь дополнительно требует `binding.current == view_ref.base_revision`
(`workspace.py:3492`). Это предусловие *снимка*.

**Почему R6 лишний.** Настоящая защита от потерянной правки — `_plan_source_identity`
(`:3631`): он открывает файл по пути и требует `_hash_fd(fd) == inputs.old_sha256`, иначе
`STALE_REVISION`. Это per-file CAS. R6 не добавляет ни одного нового запрета на запись —
он только расширяет множество отказов на «кто-то опубликовал *другой* файл».

**Почему это важно признать ошибкой.** Мутационный тест E288 («снятие сравнения базы
позволило опубликовать кандидат после постороннего коммита») закрепляет **неверный**
инвариант: он считает багом успешную публикацию патча поверх постороннего изменения.
Это тот самый случай «тест обслуживает не ту задачу». R6 был моим предложением в
Q89-мемо (R6) — здесь я его отзываю.

**Фикс.** Убрать сравнение базы из `_closed_candidate_reader` (только плановая ветка;
`publish_view` не трогать). Остальное в этой функции (provenance вида, генерация,
актор, principal, writer) остаётся — см. D3-инвариант ниже.

**Что остаётся fail-closed после удаления:**

```text
proof вида остаётся          -> чужая/мёртвая capability по-прежнему UNAUTHORIZED
status OWNED + active_actor  -> грант не перенацелен на другой namespace
generation == view.generation-> вид из прошлой эпохи не публикует
principal                    -> чужой процесс не публикует
binding.writer is None       -> мёртвый writer не публикует
closed gate + STOPPING       -> публикация только после STOP_VIEW
terminal.json == view_ref    -> терминальность доказана, а не предположена
old_sha256 файла             -> правка не затирает чужую правку того же файла
```

### Класс B — «необратимость без наблюдения»

#### D4. Потерянный ответ превращается в неотличимую ошибку

**Желаемое поведение.** Если ответ на необратимый шаг потерян, система обязана **уметь
узнать**, случился шаг или нет, и отчитаться тем же результатом.

**Сейчас.** Повтор создаёт новый `publish_request_id` (`client.py:243`) и новый вид со
старой базой; `_plan_source_identity` видит в файле уже новые байты и говорит
`STALE_REVISION` — то же самое, что при чужой правке. Исход неизвестен и запросом не
разрешается.

**Сравнение с тем, что уже есть в этой же кодовой базе.** Для sealed-пути это решено:
`verify_publication` (`workspace.py:3991`) — «докажи уже опубликованную ревизию, не
коммитя снова». То есть шаблон «наблюдать вместо повторять» в проекте уже принят.

**Фикс (и он крошечный).** `_plan_prepare` (`:3521`) уже считает дерево-результат от
`binding.current`: `entries` + `tree_sha256`. Значит:

```python
inputs = self._plan_prepare(binding, plan_ref, buffer, operation_id, deadline)
if inputs.tree_sha256 == binding.current["tree_sha256"]:
    return self._plan_receipt(inputs, binding.current["revision_id"], already=True)
```

Смысл: «дерево, которое я собираюсь получить, уже является текущим деревом» — значит
публикация состоялась (моя или эквивалентная ей). 6 строк, ноль нового хранилища,
ноль персистентных грантов, работает после рестарта.

Порядок обязателен: сначала D3 (убрать равенство базы), иначе до этой проверки не дойти —
`_closed_candidate_reader` отобьёт раньше.

#### D5. «Вид сохраняется» — фикция

**Желаемое поведение.** Заявление «вид сохраняется для разрешения» подразумевает, что
позже кто-то сможет им воспользоваться.

**Сейчас.** На неопределённости адаптер оставляет вид и **ничего не сохраняет**:
`view`, `view_capability`, `publish_request_id` — локальные переменные `publish_candidate`
(`client.py:196`,`:220`,`:243`), `uncertain` — тоже локальная. После `raise` от объекта
остаются только `_base_revision` (устаревшая) и владелец гранта. Комментарий
`client.py:269-271` («the candidate view is retained… no fresh request id can accidentally
turn a lost PUBLISH into a second commit») описывает намерение, которого код не исполняет.

**Фикс.** Заявление убрать. Резолюция — не «сохранить вид», а D4 (наблюдение) + CT107 для
случая, когда наблюдение недоступно.

#### D6. Реплей журналом не может быть механизмом разрешения

**Желаемое поведение.** Механизм разрешения неопределённости не должен требовать хранения
секрета между попытками.

**Сейчас.** Точный реплей требует совпадения `ReplayBinding` **и** `hmac(original_proof)`
(`supervisor.py:147`) — то есть той же capability. Хранить capability между попытками
значит положить bearer-токен в состояние проекта, что §7 прямо запрещает
(«no token fields»). Значит выбранный в E288 механизм («exact replay is checked at the
supervisor journal, not by a content hash») **несовместим с собственным требованием §7**
в единственном сценарии, где он нужен.

**Фикс.** Оставить журнал как есть (он хорош для защиты от двойного эффекта в пределах
процесса), но не полагаться на него. Разрешение — наблюдением (D4).

#### D7. `revision_id` зависит от попытки

**Установлено.** `_derive_revision_id` (`:244`) хэширует манифест, включающий
`operation_id` = `op-<request_id>` (`service.py:825`). Поэтому одна и та же публикация
двух попыток даёт разные идентификаторы ревизий.

**Оценка.** После D4 это **не мешает**: сравнение идёт по `tree_sha256`, а не по
`revision_id`. Трогать не нужно — и это экономит весь churn с перегенерацией пинов,
который я предлагал в прошлом разборе. Зафиксировать как известное свойство:
идентичность ревизии = «переход», а не «содержимое».

### Класс C — «грант как строка»

#### D8/D9/D10. Где именно утекает грант

**Желаемое поведение.** Bearer-грант существует только как значение внутри `execution`,
не печатается, не сериализуется, не передаётся по границам модулей; его нельзя случайно
положить в событие, артефакт или tool-результат.

**Что уже есть в проекте (и не используется).** `GrantReply` (`types.py:134`):

```text
@dataclass(frozen=True, repr=False)     # не печатается
class GrantReply:
    capability: str                     # единственное место, где грант — поле
    def to_wire_result(...)             # отдаёт capability наружу осознанно
    def to_journal_result(...)          # ПРОВЕРЯЕТ, что гранта нет в JSON (§execution-grant-journal-projection)
```

Дисциплина «грант не попадает в журнал» реализована и работает — внутри `execution`.
Дальше начинается дыра: клиент берёт `created["capability"]` и кладёт в обычную строковую
переменную (`client.py:217`), адаптер кладёт в `self._owner_capability` (`:178`),
`ManagedBashExecutor` — в `self._capability` (`:323`). Два объекта композиции хранят
сырые OWNER-гранты как `str`, вне всех проверок `GrantReply`. Один удачный
`logging.debug(vars(obj))` — и в логе полномочия на запись всего дерева на всю генерацию.

**Фикс (тип, а не переписывание).**

```text
1. client.request(..., grant: GrantReply | None) вместо capability: str | None.
   Клиент разворачивает .capability в самый последний момент, внутри encode_json.
2. Ответ CREATE_VIEW/PIN_READER сразу оборачивается в GrantReply (repr=False).
3. Порт CandidatePlanPublisher не меняется; адаптер получает client + binding,
   гранта не хранит вовсе.
4. Проверка: `assert "_capability" not in vars(obj)` и `repr(obj)` без hex —
   как тест, а не как ревью-дисциплина.
```

**Стоит ли переносить verb в клиент (удалить адаптер)?** Да, и вот почему это не «ещё
один слой»:

- §7 требует, чтобы гранты кэшировал и выбирал `ExecutionClient` — значит verb, который
  ими пользуется, должен быть его методом, иначе требование невыполнимо в принципе;
- адаптер дублирует проверку, которую уже делает контроллер: `client.py:258-265`
  сравнивает `published_ref` с посчитанным sha, а `workflow_controller.py:2310`
  сравнивает `ref` с `expected` ещё раз — два словаря ошибок на один факт;
- удаляется ~150 строк и один объект, который надо передавать через композицию.

Итог: `ExecutionClient.publish_plan(binding, source, candidate, deadline) -> PlanRef`,
порт контроллера тот же, класс-адаптер удаляется целиком.

### Класс D — «композиции нет»

#### D12/D13/D14. Один дефект, три симптома

**Желаемое поведение.** Есть ровно одна функция, которая создаёт managed-исполнение для
прогона; всё, что ниже, получает готовый `(client, binding)` и не умеет собрать его само.

**Сейчас.** Ноль конструкторов `ExecutionClient` в `src/`; `RunContext`
(`session/manager.py:71`) — пять полей про lifecycle; `_session_manager_for_args()` не даёт
provisioner'а; `_cmd_workflow()` не передаёт publisher (`cli.py:1431`); типа
`ExecutionBinding` нет вовсе.

**Фикс.**

```text
ExecutionBinding  (frozen, без секретов и без revision)
    namespace: NamespaceRef
    workspace_id: str
    run_id: str
    # client передаётся рядом, а не внутрь: binding остаётся сериализуемым фактом

managed_execution_for_run(...) -> (ExecutionClient, ExecutionBinding) | None
    единственный конструктор клиента в src/; вызывается из managed-композиции
    рядом с workspace_provisioner, не из CLI
```

Одно поле `execution: ExecutionBinding | None` в `WorkflowContext` и в `SessionState`.
Не три, не объект-контейнер: `client` живёт в композиции, `binding` — факт о прогоне.
Это снимает мой прошлый вывод D20 (отдельный `ExecutionContext`) как избыточный.

#### D15. Вложенные прогоны: HANDOFF однонаправленный

**Установлено.** `_handoff_owner` (`workspace.py:1467`) требует
`target.parent_run_id == namespace.run_id`. Значит передать грант можно только **вниз**,
ребёнку; ребёнок вернуть его родителю не может (у родителя `parent_run_id` — дед).

**Следствие.** «Дать каждому вложенному прогону свежий binding через handoff» (формулировка
Q90) означает: после первого вложенного прогона родитель теряет право публикации до конца
сессии. Это не баг кода, но и не деталь реализации — это продуктовое решение, которое
надо принять явно:

```text
(A) родитель публикует свой план ДО передачи гранта, ребёнок — после; после возврата
    родитель публиковать не может (детерминированно, однонаправленно);
(B) в managed-режиме вложенные invoke_workflow запрещены (fail-closed), пока не появится
    «возврат гранта» как отдельная операция;
(C) ввести возврат (меняет 19→20 операций и инвариант «один мутатор»).
```

Рекомендация: **(B)** в этом шаге. Она не требует кода в субстрате и не создаёт иллюзию.

## 8. Что такое «managed режим» сегодня (ответ на вопрос оператора)

### 8.1. Что хотели и зачем

Определение из E197-документа (`execution-workspace-and-i02-i03-scope-decisions-2026-10-15.md`),
сведённое к четырём гарантиям:

| Гарантия | Зачем | Где сказано |
|---|---|---|
| **Trust = право принимать authoritative решения или исполняться вне project-code boundary**; всё, что исполняет байты проекта (imports, conftest, pytest, build hooks, shell), идёт в cell | контроллер держит provider-ключи и deploy-ключ; read-only mount защищает от записи, **не от чтения** (§2.1) | §1.1, §2.1, §2.2 |
| **Один exclusive managed-writer lease на canonical workspace**; owner — workflow; читатели видят последнюю опубликованную ревизию | два писателя (chat и вложенный workflow) не должны чередоваться; «disjoint filenames не доказывают semantic independence» | §4.1, §4.2 |

| **Chat → workflow → chat с stable checkpoint**: chat-дельта публикуется в R1, workflow стартует от R1, после возврата chat берёт свежий вид от R2 | вложенный workflow не должен работать на стейл-плане, а chat не должен продолжать мутацию во время workflow | §4.4 |

Cells (Docker) существуют ровно ради первой строки: worker — среда исполнения tools,
не четвёртая LLM-роль (§3.1); supervisor держит единственный Docker-сокет (§3.3);
bubblewrap не нужен, потому что деплой уже Docker-ный.

Задел под суб-агентов (§4.5): owner делегирует **attenuated** capability, ребёнок получает
отдельный writable view, возвращает candidate, owner сам компонует в свой вид. `HANDOFF`
(I03-LIVE-27, CT113) — примитив для этой будущей схемы.

### 8.3. Почему это ощущается как каша: в слово «managed» склеены три разные гарантии

```text
                        ┌─ lease  ──────── один писатель среди managed-компонентов (мьютекс)
managed = «workspace» ──┼─ views  ──────── правки модели не попадают в canonical напрямую
                        └─ cells  ──────── код проекта вообще не исполняется рядом с ключами
```

Они независимы и включаются в разном порядке. Важное следствие:

- **lease + views** дают *функциональную* корректность (никто не перетирает, публикация одна).
  Это можно включить без Docker вообще.
- **cells** дают *содержание* (containment): без них shell модели — второй писатель,
  и «один писатель» остаётся договорённостью. Это уже про безопасность, а не про фичи.

E197-документ сам это фиксирует: «Произвольный host editor/root может обойти managed lease.
Это вне гарантий протокола» (§4.2).

То есть Q90 — кирпич №2, и он маленький. Настоящий размер задачи задаёт №1, а не №2.

## 9. Решения по четырём вопросам

### 9.1. R6 снимается (принято)

Меняется ровно три вещи: `workspace.py:3492` (снять сравнение в плановой ветке),
`tests/` (мутант «вернуть сравнение» становится наоборот — тест «публикация после
постороннего коммита проходит»), `ledger` (реверсия R6 с причиной: «патч не наследует
предусловия снимка»). Sealed-путь не трогается.

### 9.2. `ExecutionClientPlanPublisher` удаляется (решение ассистента)

Форма после удаления:

```text
ExecutionClient.publish_candidate(binding, source, candidate, *, deadline) -> PlanRef
    весь сага-путь: CREATE_VIEW(null base) → WRITE_FILE → STOP_VIEW → PUBLISH → RELEASE
    гранты достаются из внутреннего кэша клиента по binding.generation

BoundPlanPublisher (frozen dataclass, 2 поля, 1 метод)
    client: ExecutionClient
    binding: ExecutionBinding
    publish_candidate(...) -> client.publish_candidate(binding, ...)
```

`BoundPlanPublisher` типом не может содержать токен: у него нет такого поля, а `frozen`
запрещает добавить. Это и есть «closed by construction» вместо «проверено ревью».

Почему не оставить адаптер: адаптер с грантом = **один publisher на один прогон**. Для
вложенного `invoke_workflow` это означает «второй publisher ⇒ второй грант или handoff».
Второй грант невозможен (один писатель), значит handoff — а он двигает грант и меняет
актора, что ломает §4.4 (chat после возврата обязан снова получить право). С `binding`
как данными вложенный прогон просто вызывает тот же клиент.

### 9.3. Вложенные прогоны: `active_actor` принимает потомка (решение ассистента)

Три варианта, честно:

| Вариант | Что происходит | Цена | Риск |
|---|---|---|---|
| (A) handoff в ребёнка | грант переезжает, `active_actor` = ребёнок | ноль кода в субстрате | однонаправленно: родитель получает право только через `release` ребёнка и **новую генерацию**; смерть ребёнка в середине оставляет workspace в `OWNED` с грантом, которого ни у кого нет |
| (B) запретить вложенные | fail-closed | ноль | исходная цель недостижима |
| **(a′)** `active_actor` = владелец **или его потомок** | грант не двигается, генерация не меняется | одна предикатная функция + 8 сравнений заменяются на неё | авторитет расширяется на потомков — но parent-link и так controller-attested (Q85/§7.1) |

Рекомендация — **(a′)**, по двум причинам: она не двигает грант (значит не создаёт
«висячего OWNED»), и она попутно закрывает класс «авторитет сравнивается на равенство
в восьми местах» — все восемь заменяются одним `_acts_as_active_actor(metadata, namespace)`,
как уже сделано для `_settled`.

Замечание, поправляющее меня же: «родитель теряет право навсегда» — неточно. После
`release` ребёнком workspace становится `AVAILABLE`, и родитель может `acquire_writer`
снова. Теряется не право, а грант и **генерация** (все пины родителя становятся мёртвыми).

### 9.4. `already_published` — да, и плюс одно следствие

Форма: в `_PUBLISH_REPLY` (`protocol.py:145`) добавляется `already_published: boolean`;
cross-field правило — `true` допускается только когда `_plan_prepare` дал
`tree_sha256 == binding.current["tree_sha256"]`. `operation_id` в этом ответе —
собственный `op-<request_id>` этого запроса (не чужой): durable-запись ревизии —
`tree.json` = `{schema_version, revision_id, tree_sha256, entries}` (`workspace.py:180`) —
**не хранит `operation_id`**, поэтому вернуть исходный id честно нельзя, а подставлять
чужой — врать.

Следствие, которое стоит сделать тем же шагом: в *плановом* манифесте
(`workspace.py:3548`) поле `operation_id` участвует в `_derive_revision_id`, но не попадает
в `tree.json`. Значит идентификатор плановой ревизии **невычислим из durable-фактов**:
после `_clear_intent` его нельзя ни проверить, ни воспроизвести. Предложение: убрать
`operation_id` из планового манифеста (оставив его в `intent.json` для recovery-корреляции).
Тогда `revision_id` становится чистой функцией durable-фактов. Sealed-путь не трогать:
там манифест — durable `sealed.json`, и его op id честно хранится. Цена: одна инвертированная
проверка (`tests/test_workspace_publication.py:2590`) и никаких перегенераций литералов
(пины `rev-…` в тестах не используются — проверено `grep`).

### 9.5. Переименования (ответ на D17)

Принцип: имя должно называть роль, а не надежду. Сейчас `.fa/admission/` — это «где лежит
черновик планировщика», хотя «admission» — это ворота приёмки.

## 10. Почему I03 закончился компонентами без композиции

Короткий ответ: **план был правильным, а критерий «сделано» — на единицу, а не на путь.**
Ниже три механизма, каждый подтверждён артефактом репозитория.

### M1. Договор и kill-директива описывали тело, а не доставку

Форма контракта: `[FUNCTIONAL] … kill: remove-call <производитель>`. Мутант удаляет **тело**
производителя, и банк падает — значит тело нужно *этому тесту*. Продукт, у которого нет
вызывающего, для такого оракула невидим: удалять нечего, тест зелёный.

Показательно, какие директивы где:

| Контракт | Форма kill | Следствие |
|---|---|---|
| CT105 (seal) | `publication.py::seal_view -> _validate_sealed_tree` | ребро **внутри** модуля |
| CT106/CT107 (publish/recovery) | внутренние пары того же модуля | то же |
| CT96 (invoke_workflow → managed acquisition) | `workflow_tool.py::handler -> _run_planner_managed_workflow` | ребро **через** границу модуля — и это единственный тип, который заметил бы «нет композиции» |

Директивы второго типа — ровно у тех контрактов, чьи STEP'ы остались `[ ]` (SLICE5,
SLICE2 STEP6). То есть оракул, который мог бы поймать дефицит, стоял на незакрытых шагах,
а закрытые (E260–E288) проверялись внутренними рёбрами. Отсюда 572 зелёных теста при нуле
вызывающих: банк честен относительно «если вызовут, работает» и ничего не говорит о
«вызовет ли кто-нибудь».

### M2. Фронт работ всегда был внутренним

Порядок зависимостей в самом инкременте (`C. Dependency order for the remainder`):

```text
1. A1  Q74 checkpoints            — внутренний (политика + банк)
2. A4  inventory completion       — документ
3. A3  CANDIDATE publish (wire)   — внутренний (wire + примитив)
4. A5  caller cutover             — ЕДИНСТВЕННЫЙ шаг, видимый пользователю
5. A6  managed verifier
6. A7  managed acquisition (Q70)  — второй видимый шаг
7. A8/A9 SLICE6 + tests/integration — проверка композиции
```

Правило инкремента «ни один STEP не тикается, пока не закрыт весь SLICE» — правильное само
по себе — означало, что **легальной следующей работой всегда была внутренняя**: у A1/A3/A4
нет предшественников, у A5 есть три. Агент каждый раз честно выбирал разблокированное.
В результате ~30 E-записей подряд не меняли поведения продукта, и ни одна из них не могла
этого заметить: «не тикаю STEP» — правда, но не сигнал.

### M3. Каждый стык закрывался дублем, а сборки не было ни в одном тесте

Порт `CandidatePlanPublisher` в тестах контроллера реализован дублем
`_CT91TestPlanPublisher` (`tests/test_verify_gate_live.py:3530`). И этот дубль **заново
реализует удалённый продовый писатель**: проверку `source-changed`, скоуп, запись во
временный файл, `os.replace`, fsync каталога.

То есть прод-логика переехала в тест-дубль, а оракул утверждает только «контроллер правильно
зовёт порт». Единственный артефакт, который поймал бы «сборки нет», — `tests/integration/`
(пункт A9 плана) — не существует; он же последний в порядке.

### M4. Конкретная регрессия, а не «недоделка»

`E288` (`5f1c292`) — big-bang cutover сделан в обратную сторону. Диff `plan_promotion.py`:
**−138/+17**. Удалён `publish_plan_buffer` (`8b1cc95:plan_promotion.py:183`) — рабочий
host-писатель с target-keyed lock, точными байтами, `_checked_source` CAS по sha, проверкой
режима и запретом отката. Замена — порт, которого **никто не поставляет**.

Следствие для продукта, проверенное по коду `5337ded`:

```text
fa workflow --plan  →  _admit_plan                      (workflow_controller.py:2486)
   план не PASS → route=RETRY → _run_admission_repair    (:2401)
      планировщик вызывается и тратит попытку            (:2431)
      кандидат читается и валидируется                   (:2444, :2453)
      _promote_validated_plan(publisher=None)            (:2276)
         → PlanPromotionError("prepare-failed")          (:2293)
   → _admission_error → «admission blocked: prepare-failed»
   → прогон завершается FAILED
   и всё это время кандидат уже удалён в `finally`       (:2455-2457)
```

Это не «фича не подключена». Это **регресс**: до `5f1c292` repair работал, после — нет, и
валидный исправленный план уничтожается после того, как за него заплатили вызовом модели.
Правило, которое нарушено, звучит так: *удалять старый писатель можно только когда новый
уже кем-то поставляется; в одном коммите с «компонентом» — нельзя.*

### 10.5. Что это не отменяет

Твоя гипотеза «контракты + kill-check решают проблему вакуума» верна **внутри** модуля и
неверна **между** модулями. Разница в одном слове: контракт описывает, что модуль обещает
вызывающему, но не кто этот вызывающий. У I03 же 25 контрактов и ни одного контракта вида
«команда пользователя X меняет наблюдаемое поведение Y».

## 12. Правило, чтобы это не повторилось (одно предложение + два мутанта)

> Единица считается сделанной только тогда, когда существует команда, которую может набрать
> пользователь и чьё наблюдаемое поведение меняется; у каждого контракта два мутанта —
> «удалить тело» и «удалить единственного вызывающего».

Формально к DoD добавляется одна строка и один столбец:

```text
| Единица | Команда, меняющая поведение | Что наблюдает пользователь |
| A5      | fa workflow --plan …        | прогон доходит до coder'а  |
```

Столбец не может быть пустым у закрытой единицы. Для внутренних единиц (политика recovery,
валидатор) честное значение — «через A5», то есть они наследуют его от ближайшего предка,
у которого оно есть; если предка нет — единица не закрывается.

Второе следствие, дешёвое: в ledger у каждой E-записи поле `user-visible:` (`yes/no` +
команда). Тридцать `no` подряд — это не повод для тревоги, это повод проверить, почему
фронт работ такой.

## 13. Почему `publish_plan_buffer` удалили и как восстанавливать по-настоящему

### 13.1. Причина была, и она записана

Дословно из плана инкремента (не реконструкция — цитаты):

- `increment-03…md:370` — «must be moved onto the authority's `publish` of a CANDIDATE
  view, **deleting that transport in the same change so exactly one writer owns the
  canonical plan**».
- `:376` — «`plan_promotion.publish_plan_buffer` is **deleted** in the same change
  (**R3 — a retained fallback is a second writer by another name**)».
- `E287` (`:3395`) — «The latter path is a second writer and must disappear in the same
  change».
- `:1182` — «writers fails closed instead of silently forking the plan; the switch to a
  single writer must delete…».

Мотив не «почистить код», а **форк**: два маршрута записи одного файла с разными
инвариантами — это ровно тот класс, ради которого построен весь I03. Формально
требование корректное и я его не оспариваю.

Нарушено не требование, а **парность**: «in the same change» означает «удаление и
активация — один коммит». `5f1c292` сделал половину пары — удаление — и назвал это
cutover. Второй половины (композиция, которая поставляет порт) не было ни в нём, ни
после.

### 13.2. Почему «просто вернуть писатель» — неправильно (это не legacy-код)

Соблазн: вернуть `publish_plan_buffer` из `8b1cc95:plan_promotion.py:183-221`. Он писал
канонический файл напрямую — и именно поэтому несовместим с моделью ревизий супервизора:

```text
workspace.py:1303  def _unchanged(binding, deadline):
                       digest = self._snapshot(binding.source, ...)[1]
                       if digest != binding.current["tree_sha256"]:
                           self._healthy = False
                           raise SupervisorError("CORRUPT_STATE")
```

`binding.current["tree_sha256"]` — хэш дерева, которое видел супервизор. Host-писатель
меняет canonical **в обход** него, поэтому следующая же managed-операция видит
расхождение и помечает workspace нездоровым (`_healthy = False` → карантин по `_load`).

Значит host-писатель — не «старый путь, который ещё работает». Это путь, который
**портит** состояние ревизий в тот момент, когда супервизор уже владеет байтами. После
деплоя full I03 он был бы мёртвым кодом, который при случайном включении ломает
workspace. Восстанавливать его — значит вернуть дефект, а не функционал.

### 13.3. Что именно восстанавливать: SUPPLIER, а не писатель

Функционал, которого не хватает, — не «умение писать план» (оно есть в
`WorkspaceAuthority.publish_candidate_plan`, `workspace.py:3399`). Не хватает **того, кто
соединяет вызывающего с этим умением**. Поэтому восстановление — три шага, ни один из
которых не пишет файл мимо субстрата:

```text
1. Fail-fast precondition (до всякой траты денег)
   В _admit_plan, ПЕРЕД _run_admission_repair (workflow_controller.py:2401):
       if ctx.plan_publisher is None: → PlanPromotionError("managed-execution-absent")
   Следствие: repair не запускает планировщика, не создаёт кандидата, не удаляет его в
   finally (:2455-2457) и не маскируется под «плохой план» (:2291).
   Цена: 6 строк. Это не фикс функционала — это честность до его появления.

2. Единственный поставщик (это и есть Q90)
   ExecutionClient.publish_plan(binding, source, candidate, deadline)   — verb в клиенте
   ExecutionBinding(namespace, workspace_id, run_id)                    — данные, без токена
   managed_execution_for_run(...) -> (client, binding) | None           — единственный
                                                                          конструктор
   BoundPlanPublisher(client, binding)                                  — то, что видит
                                                                          контроллер
   Порядок обязателен: 1 → 2, иначе (2) без (1) снова маскирует отсутствие.

3. EDGE-мутант из §12 (доказательство класса, а не экземпляра)
   Тест на композиционном корне: для КАЖДОГО входа, который доходит до
   _promote_validated_plan (`fa workflow --plan`, `fa run chat` → invoke_workflow →
   дочерний workflow), publisher не None.
   Мутант: удалить аргумент в строке композиции → тест падает.
   Это тот самый тест, отсутствие которого позволило E288 выглядеть завершённым.
```

### 13.4. Чего в этом плане сознательно нет

| Не делаем | Почему |
|---|---|
| второй реализации коммита (host + managed) | даже взаимоисключающие, они разойдутся в инвариантах; а после деплоя host-ветка не используется никогда — это код, который нельзя проверить продуктом |
| постоянного fallback «если супервизора нет — пишем сами» | это и есть «second writer by another name», прямо запрещённый R3 |
| «host mode» как отдельного режима работы | режим без супервизора = режим без cells; он вернёт ту самую дыру, ради которой строился I03 |
| восстановления `publish_plan_buffer` ради тестов | тест-дубль `_CT91TestPlanPublisher` (`tests/test_verify_gate_live.py:3530`) уже исполняет эту роль и, по §12, не должен реализовывать продовую логику — его место занимает композиционный тест |

### 13.5. Один открытый вопрос (нужно решение)

Кандидат уничтожается в `finally` (`workflow_controller.py:2451`) **до** попытки
публикации. Если публикация провалится (stale, uncertain, отсутствующий supplier), работа
планировщика исчезает бесследно — в `admission.json` остаётся только sha.

```text
(A) оставить как есть: кандидат — временный артефакт, sha в admission.json достаточно
(B) при провале публикации сохранять точные байты в приватный каталог запуска

```

Предложение: **(B)**, потому что оплаченный вызов модели иначе не воспроизводим, а цена —
одна запись в уже существующий приватный каталог.

**Решение оператора (2026-10-31): (B).** Реализация — CT119 в SLICE7 (каталог берётся тот же,
где уже живёт черновик планировщика; cap не нужен, число попыток ограничено `planner_limit`,
а имя файла — контентный хеш). См. §14.1 G4-G5 и §14.6.

### 14.0. Траектория: что в черновике уехало не туда

**D1 [подтверждено] — CT119 черновика дублировал SLICE5.** Черновик активировал вложенный coder

уже сейчас: неуправляемый дочерний запуск получает `managed-execution-absent` **до** вызова

### 14.4. Q91 — сначала как он был поставлен, и почему он снят (см. §15)

**Вопрос.** Откуда контроллер берёт адрес супервизора?

Факты: `ServiceConfig` требует `socket_path` и `controller_uids` (`service.py:116-142`),
читается из файла (`read_config_file`, `:290`); в пользовательском конфиге `fa` такого ключа
нет (`src/fa/config.py`), `ExecutionClient` конструируется только вручную. Ни один из двух
сценариев оператора (`fa run chat`, `fa workflow`) сегодня не может получить управляемый
поставщик без нового источника конфигурации.

Варианты:

```text
(A) ключ в существующем конфиге fa:  {"execution": {"service_config": "<path>"}}
(B) переменная окружения FA_EXECUTION_CONFIG
(C) вывести из state_root супервизора (неявно) — отвергается: путь сокета не выводится
```

Предпочтение агента: **(A)** — конфиг уже путь операции (`--config`), значение проверяемо, и
отсутствие ключа даёт честное `None` → `managed-execution-absent`. Цена: одна схема конфига,
документация и тест «неизвестный ключ отвергается». Решение за оператором; до него STEP8
остаётся BLOCKED по этой части, остальные шаги слайса независимы.

**Снято как вопрос (2026-10-31).** Оператор спросил, нужен ли вообще `socket_path` и как новый
модуль может не иметь пути взаимодействия с текущим кодом. Ответ: адрес нужен (клиент UDS не
может его выдумать), но *решения* здесь нет — есть четыре строки работы, и я ошибочно назвал их
открытым вопросом. Путь взаимодействия существует и уже в коде: `fa/config.py:44
DEFAULT_CONFIG_PATH` = `~/.fa/config.yaml`, файл читается контроллером при старте, а формат
сервисного JSON уже валидируется `service.read_config_file` (`service.py:290`). Ключ
`execution: {service_config: <path>}` — это ссылка на существующий файл, а не новый формат;
переменная окружения была бы вторым ответом на один вопрос. Поэтому Q91 закрыт внутри STEP8
(`DEFAULT_CONFIG_PATH` → ключ → `read_config_file` → `socket_path` + uid), а не отдельным
решением; EDGE-мутант шага удаляет `plan_publisher=` из `cli.py:1431`, то есть без рабочего
источника эндпоинта композиция не может стать сиротой — тест этого не даст.

## 15. Сосуществование SLICE5 и SLICE7 — и два соседних конфликта (2026-10-31)

Проверка по просьбе оператора: «SLICE5 ещё не закончен; проверь, что SLICE5 и SLICE7 корректно
сосуществуют». Проверялось: зависимости, владение производителями, ссылки на символы, общие банки,
производные числа DoD. Ниже — только то, что подтверждено кодом или текстом плана, с file:line.

### 15.1. [подтверждено] SLICE5 ждал поставщика, которого нет ни в одном слайсе

`SLICE5 STEP2` содержал: *«this step is blocked until SLICE4/A5 supplies the managed client
composition (A5 itself waits for A3/Q89 and A4)»*. Проверка: `git grep "ExecutionClient(" src` —
пусто; «A5» не имеет ни шага, ни владельца, ни EDGE-мутанта. То есть SLICE5 был заблокирован
неопределённо долго — тот же класс «порт без поставщика», который закрывает SLICE7, только со
стороны потребителя.

**Правка.** `SLICE5 DEPS: SLICE4, SLICE7`; STEP2 указывает на `SLICE7 STEP7` (`publish_plan`,
удаление адаптера) и `STEP8` (`managed_execution_for_run`, `BoundPlanPublisher`), запрещает
строить `ExecutionClient` на месте и забирает себе то, что действительно его — расширение
авторитета: семь сравнений `workspace.py:1385,1891,2125,2572,3486,3804,4028` и `_owner_only`
(`:2735`) → один `_acts_as_active_actor`.

### 15.2. [подтверждено] порядок был циклическим, и «managed provisioner» не мог существовать

Три текста противоречили друг другу:

- `SLICE2 STEP3`: «inject the managed provisioner into the existing SessionManager»;
- `SLICE4 STEP2`: «The managed provisioner was ALREADY injected into SessionManager in SLICE2 STEP3»;
- код: `ManagedProvisioner.__init__(authority: WorkspaceAuthority, ...)` (`execution/provisioning.py:37`),
  а `git grep ManagedProvisioner src` вне его модуля пуст, и ни один процесс не строит
  `WorkspaceAuthority` кроме `service.py:319`.

Как только авторитет живёт в сервисе (E277), контроллер **не может** держать объект
`WorkspaceAuthority`, значит инъекция из SLICE2 STEP3 невыполнима в принципе, а SLICE4 STEP2 не
мог получить клиент раньше, чем SLICE7 его построит. С `SLICE7 DEPS: SLICE3, SLICE4` это цикл:
SLICE7 → SLICE4 → (клиент из SLICE7).

**Правка (порядок):** `SLICE7 DEPS: SLICE3` — единственная зависимость, слайс исполняется
**четвёртым**; `SLICE4 DEPS: SLICE3, SLICE7`; `SLICE5 DEPS: SLICE4, SLICE7`; `SLICE6 DEPS:
SLICE5, SLICE7` (без изменений). Итог: 1 → 2 → 3 → **7** → 4 → 5 → 6, ациклично (проверено разбором
`DEPS` всех семи слайсов).

**Правка (владение):** инъекция переехала в `SLICE4 STEP2` (там же, где снимается fail-open
readiness); `SLICE2 STEP3` амендирован — его половина это manager-side шов (injection-ordering
test с записывающим callable `WorkspaceProvisioner`, `session/provisioning.py:66`), и в тексте
прямо сказано, почему `ManagedProvisioner` не может быть значением.

### 15.3. [подтверждено] `ProvisionedWorkspace` нельзя собрать из ответа `register_workspace`

`ProvisionedWorkspace.__post_init__` требует `tree_sha256` при `registered=True`
(`session/provisioning.py:44-60`), а маршрут отдаёт только `{workspace_id, revision_id}`
(`service.py:591`). Любой клиентский провижнер упирается в это поле; сегодня дыру маскирует
только in-process `ManagedProvisioner`, у которого авторитет под рукой.

**Правка.** Новый `SLICE7 STEP9`: `ClientWorkspaceProvisioner` в `execution/composition.py` +
поле `tree_sha256` в ответе `REGISTER_WORKSPACE` (схема, маршрут, банк) — единственный вызов
`register_workspace` в `src/`. Это не второй писатель: регистрация байтов остаётся за
`register_existing`, провижнер только переводит ответ в `ProvisionedWorkspace`.

### 15.4. [подтверждено] SLICE3 STEP3 и SLICE7 владели одной и той же ногой

`SLICE3 STEP3`: *«Exit for the leg specifically: the controller's plan write reaches the authority
through `ExecutionClient.publish`»*. Это ровно `SLICE7 CT116/STEP7/STEP8`. При `SLICE7 DEPS:
SLICE3` получался цикл «SLICE3 ждёт SLICE7, SLICE7 ждёт SLICE3».

**Правка.** Authority-половина (маршрут `publish`, удаление `publish_plan_buffer`) остаётся в
SLICE3 STEP3; контроллерная нога — SLICE7 STEP7/STEP8. В текст STEP3 добавлен амендмент и
пометка, что `inner_loop/plan_promotion.py` переименовывается `SLICE7 STEP10` в
`plan_candidate.py`, поэтому упоминания `publish_plan_buffer` там — история (функция удалена в
E288), а не текущее состояние.

### 15.5. [подтверждено] SLICE5 CT96/CT108 ссылаются на удалённую функцию

## 17. Q91 — откуда контроллер берёт endpoint супервизора (решение, 2026-10-31)

**Что нужно контроллеру, чтобы опубликовать план.** Ровно три факта: `socket_path`, `rpc_timeout_ms` и
уверенность, что он вообще контроллер (`os.getuid() in controller_uids`). Всё остальное — `approved_roots`,
`profiles`, `state_root` — нужно супервизору, не клиенту. `ExecutionClient.__init__`
(`client.py:85-93`) требует `socket_path`, `server_uid`, `rpc_timeout_ms`.

**Три кандидата и почему два плохи.**

- *env-var* — скрытое состояние: не переживает запуск из чата (`invoke_workflow`), не видно в конфиге, и
  диагностика «почему не публикуется» начинается с вопроса «а переменная была?».
- *новый ключ в `~/.fa/config.yaml`* (`execution: {service_config: …}`) — этот файл читает крошечный
  парсер, который по контракту знает только блок `capabilities:` (`config.py:1-30`, `:110-146`).
  Второй ключ = второй формат в файле, у которого один смысл, плюс вторая копия того же ответа: супервизор
  уже получил этот путь через `--config` (`execution/supervisor.py:538`). Два ответа на один вопрос — ровно
  тот дефект, который закрывает слайс.
- *файл-эндпоинт, который супервизор пишет при старте* — решает другую задачу (живость, pid), но чтобы его
  прочитать, нужен ещё один известный путь; новых поверхностей становится две, а не одна.

**Решение — один канонический путь и один валидатор.**

```
SERVICE_CONFIG_PATH = config.DEFAULT_CONFIG_PATH.with_name("execution/service.json")
# <fa home>/execution/service.json, рядом с config.yaml
```

Константа объявляется рядом с `service.read_config_file` (`service.py:290`) и становится **значением по
умолчанию** для `--config` у `supervisor.main` (`execution/supervisor.py:538`, сейчас `required=True`).
Дальше композиция делает то же, что супервизор: `read_config_file(path)` — тот же код, тот же отказ на
относительный путь/`..`/битый JSON, — и забирает `socket_path`, `rpc_timeout_ms`, `controller_uids`.
Ни нового формата, ни второго парсера, ни переменной окружения, ни автопоиска: разойтись двум процессам
негде, потому что файл — один и имя у него одно.

**Отказы (все — до вызова планировщика, через `None` → `managed-execution-absent`):** файла нет; файл
невалиден; `os.getuid()` нет в `controller_uids`; `provisioned.registered is False`. Никогда не «дефолтный
сокет» и никогда не «выданный мимоходом грант».

**Ограничение названо явно:** одна установка = один FA-home = один супервизор. Второй home — вне области
этого слайса; точка расширения — параметр функции `config_path`, а не пользовательский флаг, чтобы тесты
не заводили третий способ задать путь.

**Следствие для писателя (важно, иначе публикация не пройдёт).** `create_view` требует capability и
перепроверяет `active_actor == namespace` (`workspace.py:3739` и `_writer_proof`), а `acquire_writer` пускает
только workspace в статусе `AVAILABLE` (`workspace.py:1326-1338`). Значит грант писателя — часть
*композиции*: `ManagedExecution` держит один `GrantReply` от `ACQUIRE_WRITER` на весь запуск и отпускает его
на выходе из `run_workflow`, а `BoundPlanPublisher` берёт его на время публикации. Второй `acquire` в том же
запуске — гарантированный `WORKSPACE_BUSY`, поэтому «взять на каждый publish» неверно.

**Что изменено в плане:** CT116 (источник endpoint) и STEP8 (SERVICE_CONFIG_PATH, отказы, грант), STEP9
(релиз `tree_sha256` из register — см. §18.2).

## 18. Q93 — как менять закрытые схемы провода, не убивая журнал (разбор с примерами)

### 18.1. Механика, в трёх шагах

1. Журнал — это каталог файлов `op-<request_id>.json` (`journal.py:200-205`), по одной записи на запрос.
   Запись содержит `state: DONE` и **полный результат операции в поле `result`**:
   ```json
   {"schema_version": 1, "operation_id": "op-3f...", "request_id": "3f...", "op": "publish",
    "namespace": {"run_id": "..."}, "view_ref": {"view_id": "view-...", "base_revision": "rev-..."},
    "input_sha256": "...", "state": "DONE", "container_id": null, "cancel_requested": false,
    "result": {"workspace_id": "ws-...", "revision_id": "rev-...", "tree_sha256": "...",
               "operation_id": "op-3f...", "projection_complete": true, "plan_ref": null}}
   ```
2. Каждое **чтение** записи валидирует её текущими схемами: `_read` (`journal.py:206-235`) вызывает
   `_validate_record`, который для `DONE` делает `_check(_RESULTS[op], record["result"])`
   (`journal.py:130-131`). Схемы закрыты: `_object` ставит `required` = все ключи и
   `additionalProperties: false` (`protocol.py:25-26`).
3. Добавили обязательное поле в `_PUBLISH_REPLY` (`protocol.py:145-152`) — старая запись перестаёт проходить
   проверку, `_read` бросает `JournalError("CORRUPT_STATE")`, и это всплывает на **старте**:
   `WorkspaceAuthority.__enter__` → `journal.recover_uncertain()` (`workspace.py:965`,
   `journal.py:459-476`). Не «одна операция не сработала», а «супервизор не поднимается на этом workspace».
   Записи не переписываются и не чинятся — это улика, а не кэш.

### 18.2. Три примера, один класс

- **`already_published` в ответе PUBLISH (наш STEP4).** Старые записи publish поля не имеют → после
  добавления они невалидны. Журнал живого сандбокса — кирпич. *Это единственное journal-видимое изменение,
  которое у SLICE7 остаётся.*
- **`tree_sha256` в ответе register (бывший STEP9).** Тот же эффект, но **не нужен**: провод по спеке уже
  определён как `{workspace_id, revision_id}` (`notes/i03-execution-workspace-spec-2026-10-15.md:153`,
  `service.py:591`), а третье поле требовала только локальная проверка `ProvisionedWorkspace.__post_init__`
  (`session/provisioning.py:53-59`), и **никто в `src/` его не читает** (`grep '\.tree_sha256' src` попадает
  только в записи ревизий и `checkpoints.py`/`publication.py`). Итог: не расширяем провод, а расслабляем
  локальное правило (`tree_sha256` для registered — `None`, 64-hex проверяется, если поле есть). Ноль риска.
- **Любое будущее поле** (`projection_complete`, новый вид `plan_ref`, ещё один флаг терминальности) — тот же
  класс. Пока валидация DONE идёт по «сегодняшним» схемам, каждое добавление — ломающее изменение.

### 18.3. Варианты

| | Что делаем | Цена | Чем плохо |
|---|---|---|---|
| **A** | Версия записи становится настоящей: `schema_version` (уже есть, `journal.py:69`) → реестр `RESULTS_BY_VERSION`, v1 заморожен, writer пишет текущую версию, reader валидирует по версии записи | +1 таблица схем (копия v1), +1 строка диспетчеризации, +1 тест с посеянной v1-записью | копии литералов схем на каждый bump |
| **B** | Толерантное чтение: таблица «для v1 недостающие поля = дефолт» | меньше кода | дефолт есть не всегда (`tree_sha256` не выдумать), и остаётся асимметрия «старая запись → новый клиент»: реплей отдаёт `result` без поля, новый декодер его отвергает |
| **C** | Никогда не менять закрытые ответы, только новые операции | ноль риска | каждая мелочь — новая операция, роут, тесты; 19 операций закрыты спекой, и это уже пробовали |

### 18.4. Решение (2026-10-31): B, и без новой инструкции агенту

**Выбрано B, A отклонено.** Причины оператора приняты: A — это «слишком» (замороженная копия схем на
каждый bump и ещё одно правило, которое агент должен помнить), а старые записи читаются редко, поэтому
постоянная цена за них не оправдана. Это ровно §1.2: новый компонент обязан пройти вопрос «можно ли
заменить существующим?» — существующий `schema_version` плюс таблица на десять строк дешевле, чем реестр
схем навсегда. §1.2.5 при этом не нарушается: подстановка не молчаливая, а логируемая.

**Шов, ровно один.** В `journal.py`:

```python
_ADDED_REPLY_FIELDS = {
    Operation.PUBLISH: {
        "already_published": (False, "v1 records predate the flag; a DONE publish did the write"),
    },
}

def _complete_result(op, result) -> tuple[dict, tuple[str, ...]]:
    # fill only listed, absent fields; copy, never the stored dict
```

Два вызова, оба внутри `journal.py`:
- `_validate_record` (`:130-131`) проверяет **заполненную копию** — старая запись проходит;
- `lookup` (`:281-290`) — единственный путь, которым запись уходит наружу к построению ответа, — возвращает
  **копию** с подстановкой.

Запись на диске не меняется: пути записи (`begin`/`finish`/`mark_unknown`/`cancel`) читают сырой `_read`,
поэтому подстановка не может «улучшить» улику. Реплей после рестарта и так идёт не из журнала, а из
`CompletedReplyCache` (в памяти, `supervisor.py:355-359`), то есть ответа старой формы клиент не увидит.

**Границы (все — тестами):** лишний **неизвестный** ключ по-прежнему `CORRUPT_STATE`; в таблицу можно
только *добавленные* поля, никогда удалённые или переименованные; дефолт — константа, не выводится из
состояния workspace и не считается из других полей; для записей с `result = null` таблица не применяется.

**Наблюдаемость.** Один `logger.warning("journal.compat.filled", op=…, operation_id=…, fields=…)` на
(запись, поле) за процесс: агент видит подстановку в логах, оператор тоже. Спама на старте нет —
`recover_uncertain` читает сырые записи.

**Что это не решает и когда возвращаться:** удаление/переименование поля и поле без осмысленного дефолта
(как `tree_sha256`) — это уже не «добавка»; для них B не годится, и такую схему мы просто не делаем (R9).
Если однажды понадобится — возвращаться с версией записи (A) под конкретную задачу, а не заранее.
