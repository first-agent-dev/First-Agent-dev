## F1 — `fs_read_file` frame prints negative "below" + phantom range when window exceeds EOF  🔴 THOROUGH

**Severity:** Medium (misleading model-facing framing; no data loss) · **Status:** OPEN, deferred · **Type:** engine bug (S12.7 framing)

### Symptom
Reading a short file with an explicit `end_line` past its length produces a corrupt frame header. Live evidence (pingpong run `…1788518709`): `src/fa/__init__.py` is **5 lines**; the model requested **lines 1–30**. The frame rendered:

```
[File: src/fa/__init__.py — 5 lines total — showing 1-30 — 0 above, -25 below — continue with start_line=31 — …]
```

Three defects in one line:
1. **`-25 below`** — a negative remaining-count that reads like a truncation warning.
2. **`showing 1-30`** — claims lines that do not exist (only 1–5 were returned).
3. **`continue with start_line=31`** — a resume pointer past EOF.

### Root cause (source-verified, `4f31c06`)
`src/fa/inner_loop/tools/read_file.py`, `_file_frame_header()`:
```python
above, below = start - 1, total_lines - end  # line 147
return (
    f"[File: {rel} — {total_lines} lines total — showing {start}-{end} — "
    f"{above} above, {below} below — continue with start_line={end + 1} — …]"
)  # 149-150
```
`below = total_lines - end` is computed from the **raw requested `end`**, not the effective (clamped) window. When `end > total_lines` it goes negative. The content slice itself is correct (`lines[start-1:end]` clamps via Python slicing) — only the **header** lies. `_artifact_frame_header()` (same file) has the identical pattern.

### Trigger condition
`end_line > total_lines` on an explicit windowed read. The whole-file branch (`start == 1 and end == total_lines`) is **not** taken because raw `end` (30) ≠ `total_lines` (5).

### Contrast that pinpoints it
`s127-read-small` (`…1788520127`) read the **same** `__init__.py` with **no** line window → `start=1, end=total_lines=5` → took the `showing ALL` branch → frame correct: `5 lines, 77 bytes — showing ALL`. So the bug is specific to an explicit `end_line` past EOF; unwindowed reads are fine.

### Impact
Model briefly suspected content elision ("made me briefly wonder whether content was being elided (it wasn't) — a wasted suspicion, not a wasted call"). No data lost; costs trust in the framing + a wasted inference, not a wasted turn.

### Proposed fix (one line, both frame helpers)
```python
def _file_frame_header(rel, total_lines, start, end, text_bytes):
    end = min(end, total_lines)  # a window never extends past EOF
    if start == 1 and end == total_lines:
        return f"[File: {rel} — {total_lines} lines, {text_bytes} bytes — showing ALL]"
    ...
```
With the clamp, `__init__.py` (start=1, end→5=total_lines) takes the existing `showing ALL` branch — negative count, phantom range, and dead resume pointer all resolved at once. Apply identically in `_artifact_frame_header`.

### Regression test to add
`tests/test_s127_fs_surface.py` (or framing test): read a 5-line fixture with `end_line=30`; assert frame contains `showing ALL` (or at minimum: no `-` before `below`, and no `start_line=` past `total_lines`). Kill-check: pre-fix produces `-25 below`.

### Model's own suggestion (self-report radar)
> "if the file is shorter than end_line, content ends at the last line and `below` may be negative" … a phrase like "file shorter than window" or "no more content" would be clearer than `-25 below`.

The radar worked as designed — this bug was invisible to offline tests because no fixture exercised `end > total_lines` (`cli.py` is 3668 lines).

## F2 — LoopGuard circuit-breaker is reactive; single-turn batches + stop-at-threshold evade the deny  🟡

**Severity:** Low (acceptable per design) · **Status:** ACCEPTED, row realignment pending · **Type:** design characteristic + row defect

**Design intent (operator, binding):** the guard monitors **loopy behavior across multiple turns in a row**; it must **not** stop a run for nested/parallel tool calls within a single turn.

**Mechanism (source-verified):** `loop_guard.py handle()` — `BEFORE_TOOL_EXEC` only `_record()`s (always allows); `BETWEEN_ROUNDS` only `_scan()`s (warn/deny). `loop.py:563-580` dispatches `BETWEEN_ROUNDS` at the **start** of each batch, before it executes → each scan lags one batch behind the recorded window. Deny needs `count >= 5` (`runtime_limits.py:73-75`) at a scan, i.e. the model must **attempt another batch after the window fills**.

**Observed:** minimax batched 5 identical reads into turn 1 and stopped → no post-threshold batch → `denials[0]`, warn only. **This is correct per the design intent above.**

**Row defect:** `s127-repeat` asserts the deny fires, but its task ("repeat five times … after the fifth, stop") lets the model batch + stop, which the guard rightly ignores. **Fix:** reword to force one read per turn (multi-turn), matching what the guard actually polices; then warn@3 + deny@5 fire reliably (as gemini showed). `s127-pingpong` already does this correctly (checks for a *signal*, not a hard deny — RN11 preventive).

## F4 — `fs_read_file` artifact-retrieval path is dead: containment hook rejects `artifact_id`-only calls  🔴 THOROUGH

**Severity:** Medium-High (an advertised S12.7 feature is non-functional; wasted turns; misleading error) · **Status:** OPEN, deferred · **Type:** engine bug (schema ↔ hook mismatch)

### Symptom
The oversize-read truncation footer prints an artifact handle `[artifact: tool-result-31aad25b1eb805e9]` and the tool docs/schema describe `path` XOR `artifact_id`. But calling `fs_read_file` with **only** `artifact_id` is rejected:
```
ERROR[hook_deny]: path must be a non-empty string
```
Reproduced twice, independently:
- **artifact-follow** (`…1788524572`): model tried to follow a **valid** minted id `tool-result-31aad25b1eb805e9` → denied → **one wasted turn**, fell back to windowed reads.
- **artifact-unknown** (`…1788524906`): model probed a **bogus** id `tool-result-0000000000000000` → denied by the *same* hook, so the tool's real "artifact not found" path never ran.

### Root cause (source-verified, `4f31c06`)
The containment hook validates `path` for every path-tool and has **no awareness of `artifact_id`**:
```python
# src/fa/inner_loop/hooks/builtin.py
_FS_PATH_TOOLS = frozenset({"fs_read_file", "fs_write_file"})  # :36
...
if call.name in _FS_PATH_TOOLS:  # :132
    return self._handle_path(call.params.get("path"))  # :133
...


def _handle_path(self, path):  # :149
    if not isinstance(path, str) or not path:
        return Decision.deny("path must be a non-empty string")  # :150-151
```
The **tool itself fully supports** artifact-only reads — the hook just never lets the call reach it:
```python
# src/fa/inner_loop/tools/read_file.py
# :400-416  path XOR artifact_id preamble ("pass exactly one")
# :291      _read_artifact(artifact_id, start_line, end_line)
# :310      "artifact {id!r} not found in this run's artifact stores"  ← real not-found path
```
So `_read_artifact` (and its clean not-found steering) is **unreachable dead code** for any `artifact_id`-only call: `BEFORE_TOOL_EXEC` denies first because `params["path"]` is absent.

### Why it's a real defect, not just a rough edge
1. **Advertised-but-dead feature.** The truncation footer hands the model an artifact handle as a recovery route; following it always fails.
2. **Misleading error.** `path must be a non-empty string` names a field the model deliberately omitted in favor of the documented alternative. It reads as a schema violation, not "you can't use artifact_id here."
3. **Masks the real not-found path.** Even a bogus id never reaches `_read_artifact`'s `artifact_not_found` steering, so the model can't distinguish "bad id" from "wrong calling convention."
4. **Costs turns.** artifact-follow burned a turn; artifact-unknown's whole probe was intercepted.

### Proposed fix
Make the containment hook artifact-aware for `fs_read_file` — the artifact store is session-scoped (already contained), so an `artifact_id`-only read needs no path-containment check:
```python
if call.name in _FS_PATH_TOOLS:
    if call.name == "fs_read_file" and call.params.get("artifact_id") and not call.params.get("path"):
        return Decision.allow()  # session-owned store; no traversal surface
    return self._handle_path(call.params.get("path"))
```
Then a valid id retrieves, a bogus id hits `_read_artifact`'s `not found` steering, and the schema/hook agree. Add a regression test: `fs_read_file(artifact_id=<unknown>)` returns the not-found ToolResult (not a hook deny).

### Row defect exposed
`s127-artifact-follow` asserts the artifact_id was **followed** (a call with `artifact_id` exists) — which the model did, so it **passed despite the retrieval failing**. The assertion must check the follow-up **succeeded** (artifact content returned), which would fail and catch F4. `s127-artifact-unknown` is correctly designed — it expected `artifact_not_found` and failed, catching F4 as intended.

## F7 — `fs_run_bash` envelope `returncode` reflects the PIPELINE exit, not the real command's  🟡 CLOSED (doc + row; no runner change)

**Status:** CLOSED as documentation + live-row fixture. Not an FA runner bug — bash last-stage semantics. **Do not** wrap `set -o pipefail`. **Do not** rename `returncode`. **Do not** inject `PIPESTATUS`.

### Symptom (bash-stderr)
The model ran `python … 2>&1 | tail -n 20`. Python exited 2 (SystemExit), but `tail` exited 0, so the pipeline exited 0 and the envelope reported `returncode: 0`. The non-zero exit was masked. The model had to fall back to `PIPESTATUS[0]` / its own marker to learn the truth.

### Impact
The `s127-bash-stderr` row's objective ("non-zero exit surfaced") was **not directly exercised** — an OR-assertion (`ok:false` / stderr / `bash exited [1-9]`) could pass on IntentGuard denials or stderr-presence while the pipeline exit read 0.

### Locked close (implemented)
1. **Keep the key `returncode`.** Document it on `fs_run_bash` as the shell/pipeline last-stage exit, **next to** the tool's own "Prefer grep / | tail" steer, and tell the model: if they need the producer's status they must `set -o pipefail` **in that command** or not pipe. FA still does not inject pipefail.
2. **Fix the live row:** task forbids a masking pipe; fixture is a raising command (traceback on stderr); oracle requires `bash exited [1-9]` and must not OR with `ok:false` or stderr-presence.
3. **PIPESTATUS deferred — do not build naively.** Fallback is `subprocess.run(..., shell=True)` → `/bin/sh -c` (dash on Ubuntu: **no** `PIPESTATUS`). PTY may be bash. A `pipestatus` field filled on one path and empty/garbage on the other is worse than today's ambiguity. String-injecting `echo FA_PIPESTATUS:${PIPESTATUS[*]}` mutates the model's command; `"|" in command` is fragile (`||`, quoted `|`). If ever pursued: out-of-band bash-guaranteed wrapper, not paste into the command.

### Why not global pipefail
Every `| head` / `| grep` / `| tail` the model writes (the tool *steers* toward this) would then exit 141/1 on early close and burn turns — against forgiving-tools.

## F10 — `--detail debug` was documented as "model text per turn" but never implemented  🔴 THOROUGH (found by verifying this doc)

### How it surfaced
The operator directed "there is a capability to do so. look in cli flags" for per-turn agent messages. ### Root cause (source-verified, `4dc7c47`)
```python

    ...
    preview = text_str[:200].replace("\n", " ")  # truncated at BOTH levels

- The only `debug`-exclusive branch in the whole renderer is `:355` (`if self.detail == "debug" and d.get("ms")` → per-event ms timing). **debug = verbose + ms timing**, not full model text.
- The user-facing help (`cli_help.py:90`) only says "Console detail level" — the false promise lived solely in the internal docstring, which is why it went unchallenged.

### Why it matters
The harness's only complete per-turn LLM-text surface was the live-check script's S12.6c timeline `💬` block (reconstructed from events). The docstring claimed the console already provided it, so the script's compensation looked redundant — but removing it on the strength of the docstring would have **deleted the only full-text surface** while `--detail debug` silently kept truncating. ### Lesson
Docstrings are claims, not behaviour. The "verify its claims" pass is what caught this — every other source citation in this doc (F1, F4, F8, F9) checked out exactly at `4dc7c47`, but the one claim that drove a code change was the one that was wrong.

## F8 — Silently-ignored removed knobs are buried in `warnings[]`; a result-changing ignore is a trap  🟡

### Symptom (search-leniency)
The model passed six removed knobs (`order`, `include_tests`, `glob`, `case_sensitive`, `max_file_size`, `context_lines`). All were **accepted-but-ignored** with a per-param warning — leniency worked exactly as designed (no rejection, no wasted turn). But:
- The warnings live in a `warnings[]` array at the **end of a large JSON payload**. Model: *"easy to skim past when you're scanning for matches… the per-call warning isn't loud enough on its own."*
- The sharp edge: `glob='*.py'` was ignored, so the result **mixed `.md` files into a supposedly Python-scoped search**. Model: *"I had to mentally re-filter… If I'd trusted my own parameter, I'd have wrongly assumed the result was already Python-scoped."*

### Why it matters
This is the operator's forgiving-tools principle working — but **forgiving ≠ silent**. A silently-ignored param that *changes result semantics* (glob, include_tests) is a trap: the caller gets a plausible-looking result that doesn't match their intent, and only discovers it by reading a buried array. The leniency saved a turn on rejection but risked a wrong-scope result.

### Model's suggestion (radar)

## F9 — Truncation framing is inconsistent; `matches` mode omits the total, so the model can't size the remaining universe  🟡 THOROUGH

### Symptom (search-leniency + search-removed-mode; contrast search-modes)

```

- **matches (`:909-916`) → carries `returned`, `truncated`, `total_bytes`, `index_stats` — NO `total` match count** ✗
