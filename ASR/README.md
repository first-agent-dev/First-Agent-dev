# Локальное распознавание речи (эксперимент)

Отдельный host-side инструмент для локального распознавания русской речи.
После установки модель работает локально; первый setup и первый VAD для длинного
аудио требуют сети. Аудио вручную кладётся в `ASR/data/inbox/`; результаты
сохраняются в Markdown и JSON
в `ASR/data/outbox/`. Он не меняет контейнер First-Agent и не добавляет тяжёлые
ML-зависимости в основной `pyproject.toml`.

## Решение по модели и квантованию

В [cstr/gigaam-v3-GGUF](https://huggingface.co/cstr/gigaam-v3-GGUF) сейчас нет
FP8-файла. Есть F16, `Q8_0` и `Q4_K`. `Q8_0` — это 8-битная блочная
целочисленная квантизация GGUF, **не FP8**.

Для первого замера выбрана `gigaam-v3-e2e-rnnt-q8_0.gguf` (~249 MB): русская
модель, выдающая регистр, пунктуацию и нормализованные числа; в карточке это
вариант с наилучшим качеством среди перечисленных GigaAM-вариантов. Квант
Q8_0 в проверке автора конвертации дал идентичный PyTorch-транскрипт на их
контрольном аудио. Это хорошая стартовая точка, но не обещание такого же WER на
ваших записях.

Для эксперимента установщик также скачивает
`gigaam-v3-e2e-rnnt-q4_k.gguf` (~154 MB). Его сравниваем на тех же аудио и
потоках CPU: меньше файл, потенциально быстрее; карточка предупреждает о
небольших потерях регистра/пунктуации на отдельных словах. Если важнее только
пропускная способность, следующим сравнением может быть e2e-CTC Q8_0: автор
конвертации указывает более быстрый CTC-декодер.

**Почему CrispASR:** это C++/ggml runtime с отдельным GigaAM backend, GGUF,
CPU-инференсом, VAD и готовым текстовым выводом. Для первого опыта используем
CPU-релиз без CUDA/Vulkan: проще получить повторяемую базовую линию на
i5-1235U. GigaAM ожидает mono PCM WAV 16 kHz: уже подходящий WAV скрипт
передаёт напрямую, остальные форматы приводит `ffmpeg`. Это соответствие
контракту входа модели, а не постобработка для повышения качества.

## Требования и установка

На Ubuntu 24.04:

```bash
sudo apt update
sudo apt install -y curl
# Для MP3/FLAC и WAV, не соответствующих контракту модели:
sudo apt install -y ffmpeg
./ASR/asr setup
```

Установщик скачивает CPU-бинарник CrispASR `v0.8.43`, Q8_0 и Q4_K модели;
итого около 450 MB. Python-библиотеки не нужны — достаточно стандартной
библиотеки Python 3.11+. `ffmpeg` нужен только для преобразования аудио:
подходящий mono PCM16 WAV 16 kHz можно проверить без него. Установка проверяет
AVX2/FMA и выбирает совместимую CPU-сборку; NVIDIA/CUDA не требуются. Первый
запуск VAD для длинной записи может скачать небольшой Silero VAD в
`~/.cache/crispasr/`.

Установщик сверяет SHA256 релизного архива CrispASR и официальные SHA256 обеих
моделей, проверяет формат GGUF и сохраняет revision/hash в локальных manifests.
Модели привязаны к Hugging Face commit SHA; смена `GIGAAM_REVISION` обновляет
веса. Для альтернативной revision обязательно передайте официальные хеши обоих
GGUF. Версию рантайма можно переопределить через `CRISPASR_VERSION`, но для
любого релиза, кроме закреплённого `v0.8.43`, нужно передать официальный хеш
архива, например:

```bash
# Замените REPLACE_WITH_64_HEX_DIGEST официальной суммой релиза.
CRISPASR_VERSION=v0.8.44 CRISPASR_SHA256='REPLACE_WITH_64_HEX_DIGEST' ./ASR/asr setup

# Для другой revision укажите commit SHA и SHA256 двух файлов GGUF.
GIGAAM_REVISION='REPLACE_WITH_40_HEX_COMMIT_SHA' \
  GIGAAM_Q8_SHA256='REPLACE_WITH_64_HEX_DIGEST' \
  GIGAAM_Q4_SHA256='REPLACE_WITH_64_HEX_DIGEST' ./ASR/asr setup
```

Замена runtime активирует его для последующих запусков; стандартный runtime
также остаётся на диске. Для воспроизводимых сравнений используйте одинаковую
версию CrispASR и один и тот же `GIGAAM_REVISION`.

## Обычный запуск

```bash
mkdir -p ASR/data/inbox
cp ~/recording.wav ASR/data/inbox/
./ASR/asr run --threads 4
```

Поддерживаются WAV, MP3, M4A, FLAC, OGG/Opus, AAC, WebM и MP4 с аудиодорожкой.
Можно положить несколько файлов и обработать всю папку. Исходники сохраняются;
результат пропускается, только если совпадают метаданные аудио, модели,
CrispASR и параметры запуска, а Markdown не был изменён. Для замены содержимого
при сохранённых размере и mtime либо для безусловного повтора используйте
`--force`. Для файлов, которым надо преобразование,
лимит ожидания ffmpeg настраивается через `--conversion-timeout` в секундах
(0 — без ограничения); `--timeout` задаёт лимит одного инференса. Одна команда
`run`, `bench` или `setup` выполняется за раз: это исключает конкуренцию за CPU
и изменение моделей во время инференса. Стерео пока сводится в mono: если
в левом и правом каналах записаны разные участники, такое сведение может
ухудшить распознавание; для таких записей лучше сначала выбрать нужный канал.

Пример результата для `recording.wav`:

- `ASR/data/outbox/recording.wav.md` — отформатированный Markdown с транскриптом,
  моделью и временем;
- `ASR/data/outbox/recording.wav.json` — тот же текст и машинно-читаемые метрики.

При длительности больше 20 секунд по умолчанию включается VAD, чтобы не отдавать
GigaAM слишком длинную последовательность. Первый VAD-запуск может скачать
Silero из сети; этот download входит в время первого инференса и не отражает
скорость последующих запусков. Порог настраивается через `--vad-threshold 30`;
режимы — `--vad on|off|auto`. Число CPU-потоков задаётся
`--threads N` или переменной `ASR_THREADS`. Начальный профиль для замера — 4
потока; затем сравните 2/4/8, так как у i5-1235U есть P- и E-ядра, а лучший
режим зависит от охлаждения и лимита мощности конкретного моноблока.

Можно запустить один файл без копирования в inbox:

```bash
./ASR/asr run --audio ~/recording.wav --threads 4
```

## Процесс и управление через CLI

Новый Docker-контейнер не создаётся. Текущий `./ASR/asr run` — одноразовый
запуск: Python-обёртка стартует дочерний `crispasr` для каждого файла, ждёт
результат и завершается; отдельный процесс не остаётся висеть. Команда
`./ASR/asr bench` тоже сама завершается после замеров.

Уже доступны CLI-команды `setup`, `run`, `bench` и параметры у `run`/`bench`
(аудиофайл, модель, число потоков, VAD, принудительный повтор и таймаут).
Отдельные команды управления постоянно работающим сервисом (`server start`,
`status`, `stop`) в этой версии пока не подключены.

Сам CrispASR поддерживает persistent HTTP server: модель загружается один раз и
остаётся в памяти между запросами; есть health endpoint. Это всё ещё обычный
host-процесс, не контейнер. Если нужен такой режим, следующий шаг — добавить в
`./ASR/asr` команды `server start|status|stop`, запускать сервер только на
`127.0.0.1` и хранить PID/log в игнорируемой локальной папке.

## Эксперимент скорости и качества

1. Подготовьте репрезентативную русскую запись (лучше 1–3 минуты, без музыки) и
   положите её в `ASR/data/inbox/sample.wav`.
2. Создайте ручной эталон слов в
   `ASR/data/references/sample.txt`. В нём важны произнесённые слова; регистр,
   пунктуация и `ё/е` нормализуются. Цифры и числительные словами пока не
   приводятся к одному виду — для корректного WER запиши числа так же, как в
   транскрипте модели.
3. Запустите три повтора Q8_0 и Q4_K на одинаковых условиях:

   ```bash
   ./ASR/asr bench --threads 4 --repeats 3
   ```

4. Для проверки масштабирования по потокам повторите с `--threads 2` и
   `--threads 8`. Сравнивайте отчёты, не смешивая разные аудио и условия
   питания/фоновой нагрузки.

Первый запуск VAD может скачать Silero-модель из сети; если это произошло во
время benchmark, первый прогон может оказаться медленнее. Для чистого сравнения
после загрузки VAD повторите benchmark. Для сохранения нескольких наборов
замеров задайте разные `--output-dir`: отчёты для того же имени аудио
перезаписываются.

В `ASR/data/benchmarks/` появятся Markdown-отчёт, JSON с замерами и отдельные
тексты Q8_0/Q4_K. В отчёт попадают модель CPU, число логических CPU, ОЗУ, версия
CrispASR и Python, размеры файлов моделей, длительность клипа и параметры запуска.

- **RTF** = wall-time запуска CrispASR / длительность аудио. Меньше 1 — быстрее
  реального времени. Время включает запуск бинарника и загрузку GGUF, но отдельно
  от однократной нормализации через ffmpeg.
- **WER/CER** вычисляются только при наличии ручного эталона; ниже — лучше.
  Если эталона нет, отчёт показывает скорость и расхождение Q4_K относительно
  Q8_0, но это расхождение **не является оценкой точности**.
- На одном клипе нельзя обоснованно оценить качество в целом. Для решения
  используйте несколько записей: чистую речь, имена/термины, шумную речь и
  длинный файл; проверьте транскрипт глазами.

Получить более точный WER/CER можно только после разметки эталонного текста.
Модельная карточка сообщает средний WER 8.4% для своего e2e-RNNT evaluation;
это не ожидаемый результат конкретно на вашем аудио.

## Обработка текста

В v1 сохраняем текст GigaAM без автоматического «улучшения» — модель уже
возвращает пунктуацию и регистр, а генеративная постобработка может незаметно
изменить смысл. `ast` предназначен прежде всего для синтаксических деревьев
кода, а BM25 — для поиска по корпусу; они не исправляют ASR. Когда появится
проверенный корпус терминов, BM25 можно добавить как подсказку оператору или
для поиска по архиву, не заменяя исходную расшифровку.

## Границы эксперимента

- Я не запускал нейросеть на вашем i5-1235U: доступный здесь sandbox имеет
  другое, сильно ограниченное число CPU и нет ваших аудиофайлов. Поэтому
  численные скорость и качество намеренно не выдумываются. Команды выше
  запишут фактические показатели на вашем моноблоке.
- Первая версия запускает отдельный CrispASR-процесс на каждый файл; время
  замера включает загрузку модели. Разделения по говорящим пока нет. Для более
  частой пакетной обработки можно следующим этапом перевести worker на постоянный
  CrispASR server, который держит модель в памяти.
- Все runtime, веса, аудио, эталоны и результаты локальны и исключены из Git и
  Docker build context.
