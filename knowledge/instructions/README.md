# Инструкции по развёртыванию и эксплуатации First-Agent

Это «единая точка входа» для человека, который **разворачивает** или
**администрирует** First-Agent на выделенном сервере (AIO — «всё в одном»).
Документы разделены по сценарию использования — выберите свой:

## С чего начать

| Я хочу… | Открыть |
|---------|---------|
| **Развернуть с нуля** (новый сервер: BIOS → Ubuntu → Docker → Tailscale → первый запуск) — делается **один раз** | [`01-install.md`](./01-install.md) |
| **Обслуживать работающий деплой** (обновление, пересборка, бэкапы, перезапуск, диагностика, запуск задач) — **повседневно** | [`02-operations.md`](./02-operations.md) |
| **Усилить защиту SSH** (firewall, fail2ban, Tailscale ACL) | [`../../scripts/ssh-tailscale/README.md`](../../scripts/ssh-tailscale/README.md) |

## Как это устроено (принцип разделения)

- **`01-install.md`** отвечает за **однократный** путь «от чистого железа до
  первого запущенного агента». Сюда не входят повторяющиеся операции.
- **`02-operations.md`** отвечает за **всё повторяющееся**: обновления,
  пересборку, бэкапы, управление сервисом, восстановление и диагностику.
  Также содержит полное описание запуска задач — ручного, через workflow
  и автоматического.
- Логика усиления SSH живёт в **одном** месте —
  [`scripts/ssh-tailscale/README.md`](../../scripts/ssh-tailscale/README.md);
  обе инструкции ссылаются на него, не дублируя шаги.

Так каждый документ остаётся в пределах своего объёма и читается линейно под
конкретную задачу, а пересечений между файлами нет.

## Ролевой Цикл (Как работает Агент)

Агент работает не как одиночный процесс, а как **замкнутый цикл ролей**,
каждая из которых передаёт контекст следующей. Это повышает качество кода
и защищает от галлюцинаций LLM.

### Основной способ — `fa workflow` (автоматический)

Одна команда запускает полный цикл: общий `run-id`, `workspace` и `resume`
между ролями прокидываются автоматически.

```bash
fa workflow planner,coder,eval "Спланируй, реализуй и проверь X"
```

Режимы workflow:

| Режим | Описание | Команда |
|-------|----------|---------|
| `linear` (по умолчанию) | Каждая роль выполняется один раз | `fa workflow planner,coder,eval "..."` |
| `repair` | + ограниченные раунды coder→eval по результатам eval | `fa workflow coder,eval "..." --mode repair --max-repairs 2` |
| `adaptive` | + planner re-entry по eval route (детерминированные маршруты) | `fa workflow planner,coder,eval "..." --mode adaptive` |

Роли в цикле:

- **`planner`** (Планировщик) — читает задачу, анализирует кодовую базу
  (read-only инструменты) и формирует архитектурный драфт (`pr_draft.md`).
- **`coder`** (Кодер) — берёт план, создаёт изолированный workspace clone
  и пишет код. Не может пушить без авторизованного драфта (IntentGuard).
- **`eval`** (Оценщик) — проверяет написанный код (read-only инструменты).
  Выносит вердикт (`PASS` / `REPAIR_REQUIRED` / `REPLAN_REQUIRED` / `BLOCKED`)
  и записывает маршрут в `eval_report.json`.
- **`compactor`** (optional) — малая модель для сжатия контекста при длинных
  сессиях. Автоматически вызывается `fa run`, если объявлена в `models.yaml`
  и включён флаг `context_compaction_enabled`. Не участвует в workflow.

### Ручной способ (фолбэк)

Если нужен полный контроль, workflow можно развернуть в отдельные команды:

```bash
fa run -r planner -i work-1 "Спланируй X"
fa run -r coder -i work-1 --resume "Реализуй X"
fa run -r eval -i work-1 --resume "Проверь X"
```
